# 共感AI つむぎ

社員がつむぎと話すと、気持ちが匿名で集計され、管理者の画面には組織の傾向だけが出るソフトです。社員向けのデスクトップアプリ（Electron）と、感情ログを集計する管理者向けの API サーバー（PHP）でできています。

管理者は、ダッシュボードの「社員」タブで、社員の登録・修正・パスワードのリセット・退職（在籍に戻すこともできます）・削除ができます（展示モードでは出ません）。登録とリセットでは、仮のパスワードが1回だけ画面に出ます。管理者が本人に直接伝え、本人が最初のログインで新しいパスワードに変えるので、管理者が社員の本当のパスワードを知ることはありません。削除できるのは、退職にした社員で、直近7日間に感情の記録がない社員だけです（管理者だったときの記録も数えます）。削除すると、その社員の感情ログも一緒に消えます。記録がある社員は、最後の記録から7日たつと削除できます。「社員」タブには、感情に関わる情報は出ません。

所属（部署・新卒の区分）を変えたとき、管理者の権限を付けたり外したとき、在籍に戻したとき、仮のパスワードを発行したときは、本人あての知らせが残ります。氏名の変更、退職にすること、登録、削除では、知らせは出ません。本人は、次にログインしたときに、チャットの画面の上で知らせを見て、「確認」を押します。設定の窓には、直近90日の履歴が出ます。まだ確認していない知らせは、90日より古くても出ます。展示モードでは、知らせも履歴も出ません。

## 工夫した点

| 工夫 | 内容 | 主なファイル |
|---|---|---|
| 会話がネットに出ない | AI（Ollama と Gemma 4）も声（VOICEVOX）も、その PC の中で動きます。アプリからの通信は、許可した宛先・メソッド・パスの組だけに絞り、画面には CSP をかけています。画面から main プロセスへの頼み（IPC）は、アプリの画面からだけ受け付けます。 | `tumugi_app/net-policy.js`、`tumugi_app/ipc-guard.js`、`tumugi_app/main.js` |
| 個人を特定させない | 直近7日間に記録がある社員が10名未満の部署は、数字を出しません。危機の検知も、人数が少ないときは件数を出さず「あり」とだけ出します。集計は、記録した時点の所属で作るので、管理者があとから所属を変えたり、退職にしたりしても、その場では数字が動きません。自分のパスワードを決めてから7日たつまでの社員の記録は、あとからも集計に入れません（在籍に戻したとき、管理者の権限を外したときも、そこから7日は同じです）。管理者の記録も、集計に入れません。所属が変わったときは、本人にログイン時に知らせます。ただし、管理者は社員のアカウントを作って自分で使えるため、前もって用意すれば、人数の水増しを防ぎきれません。役割を分けていないのは、管理者が1人で運用する会社を想定しているためです。 | `tumugi_server/api/dashboard_data.php` |
| 記憶の暗号化 | つむぎが覚えた内容は、社員のパスワードから scrypt で作った鍵で AES-256-GCM により暗号化し、さらに OS の仕組み（safeStorage）で包んで保存します。鍵はメモリにだけ置きます。パスワードを変えたときは、新しい鍵で暗号化し直します。管理者が仮のパスワードを発行したときなどに読めなくなった記憶は消し、本人には、次の「はじめに」の画面で理由を知らせます。 | `tumugi_app/memory-crypto.js` |
| 見逃しを減らす | キーワード → 危ない話かの判定（返事とは別の AI の呼び出し）→ 返事、の順で動きます。キーワードに当たったときは、判定を待たずに相談先を案内し、危機として記録するかだけを判定で確かめます（言葉の一部が当たっただけの文や冗談で、部署に「危機あり」が出ないように）。返事は JSON スキーマで受け取り、壊れていたら1回だけ作り直します。 | `tumugi_app/js/safety.js` |
| 声に合わせて口が動く | VOICEVOX の音ごとの長さ（audio_query）から、口を開け閉めするタイミングを作ります。 | `tumugi_app/js/lipsync.js` |
| GPU のない PC でも待たせない | 返事の入力は前の回の後ろに足すだけにし、判定には直近の3件だけを渡して、どちらも返事のあとに次の入力を読ませておきます（Ollama のキャッシュを効かせる）。判定を直近の3件にしたのは、会話の全体を渡すと、長い会話のあとで危機を見逃しやすくなったためです。返事は届いたところから少しずつ出します。CPU だけで、文字が出るまで約27秒が5〜8秒になりました。 | `tumugi_app/js/conversation.js`、`tumugi_app/main.js` |

## 必要なもの

- Docker Desktop
- Node.js（22.12 以上。Electron 45 が求めるため）
- Ollama（新しい版。モデル：`ollama pull gemma4:e4b`）
- VOICEVOX

最初の1回だけ、Docker イメージ・npm パッケージ・Electron 本体・Ollama のモデルのダウンロードにインターネット接続が必要です。

## 起動手順

コマンドはすべて、リポジトリのルートで実行します。

1. `.env` を作り、パスワード類（`DB_PASS`・`DB_ROOT_PASS`・`DEMO_PASSWORD`）を推測されにくい値に書き換えます。記号を使うとコマンドや `.env` の読み込みで問題が起きることがあるため、英数字だけ（長め）にしてください。

   ```powershell
   Copy-Item .env.example .env
   ```

2. Docker Desktop を起動してから、サーバーを起動します。初回はイメージのビルドと、デモデータの投入が自動で行われます。

   ```bash
   docker compose up -d
   ```

3. 状態を確認します。`db` が healthy、`app` が Up、`seed` が `Exited (0)` なら成功です。

   ```bash
   docker compose ps -a
   ```

4. Ollama を起動してから、アプリを起動します。VOICEVOX は、アプリが起動時に音声エンジン（画面なし）を立ち上げ、アプリを閉じると止めます（もともと VOICEVOX が動いていれば、それを使います）。アプリを起動してすぐにログインしても、声の準備（10〜20秒ほど）を待たずに話せます。準備ができるまでの返事は文字だけです（立ち絵の下に「声は準備中です」と出ます）。

   ```bash
   cd tumugi_app
   npm install
   npm start
   ```

   最初の `npm start` のときに、Electron 本体（約160MB）をダウンロードします。あとでネットにつながらない状態で使う PC では、`npm install` のあとに `npx install-electron --no` を実行して、先に取っておきます。

立ち絵の画像はリポジトリに入っていないので、そのままではつむぎの絵が出ません（「立ち絵について」を参照）。

## デモアカウント

| 社員ID | 内容 |
|---|---|
| E001〜E048 | 一般社員（営業部・開発部・人事部・製造部 各12名、うち新卒は各部署3名の計12名） |
| A001 | 管理者（ダッシュボードを閲覧できる） |

パスワードは全員共通で、`.env` の `DEMO_PASSWORD` です。ログインしたあと、「設定」からパスワードを変えられます（展示モードでは出ません）。

初めてログインすると、感情ログの送信に同意するかを確認する画面が出ます。「送信する」を選ぶと、発言ごとの感情がサーバーに記録されます。

デモの DB で「社員」タブを試すときは、足した社員を、サーバーを起動し直す前に消してください（「社員」タブで退職にしてから、「削除」）。デモ用ではない社員が残っていると、次の起動でデモデータの投入（`seed`）が止まります（「うまく動かないとき」を参照）。

## 展示で使うとき

リポジトリのルートの `start-demo.bat` をダブルクリックします。次の順に立ち上がり、最後にアプリが展示モードで開きます。

1. Docker Desktop（動いていなければ起動して待つ）
2. サーバー（`docker compose up -d`）
3. デモデータの作り直し（`seed --refresh`。それまでの感情ログはすべて消えます）
4. Ollama（動いていなければ起動し、モデルを先に読み込む）
5. アプリ（VOICEVOX の音声エンジンは、アプリが立ち上げます）

ログインすると、つむぎが時間帯に合わせてあいさつします（「はじめに」で呼び名を入力していれば、呼び名も呼びます）。

展示モードでは、来場者どうしで話した内容が見えないように、次のように動きます。

- つむぎの記憶はディスクに保存せず、ログアウトするかアプリを閉じると消えます。
- 感情ログの送信の同意は、ログアウトのたびに消えます（来場者ごとに同意の画面が出ます）。
- モデルを60分読み込んだままにします（来場者の間があいても、最初の返事が遅くなりにくい）。

**来場者が替わるたびに、ログアウトしてください。** ダッシュボードは直近7日間の記録だけを表示するので、展示の日は毎朝 `start-demo.bat` から起動してデモデータを作り直してください。

Ollama・Docker Desktop のインストール先が違う PC で使うときは、`start-demo.bat` の先頭のパスを直します。VOICEVOX は、ユーザーごとのインストール先（`%LOCALAPPDATA%\Programs\VOICEVOX`）と Program Files の両方を探します。

| やりたいこと | コマンド |
|---|---|

| phpMyAdmin を使う | `docker compose --profile tools up -d` のあと http://127.0.0.1:8081 を開く（`.env` の `DB_USER` / `DB_PASS` でログイン） |

## CPU だけの PC をまねて確かめるとき

GPU のある PC で、CPU だけの PC の待ち時間をまねて確かめるときは、次のように起動します。

```bash
cd tumugi_app
npm start -- --cpu-only
```

Ollama へのすべての呼び出しに `num_gpu: 0`・`num_thread: 4` を付けて、CPU だけで動かします。待ち時間は、DevTools の console の `[時間]` で見ます。メニューを消しているので、DevTools は、確かめるあいだだけ `tumugi_app/main.js` の `//win.webContents.openDevTools();` のコメントを外して開きます（終わったら元に戻してください）。

## Electron の版を上げるとき

今は Electron 45 を使っています。45 のサポートは、2027年4月ごろまでの予定です（https://releases.electronjs.org/schedule ）。サポートが終わる前に、サポート中の版に上げます（およそ半年に1回）。

Windows のスマート アプリ コントロールがオンの PC では、出たばかりの版の Electron 本体が止められて、`npm start` が `Error: spawn UNKNOWN` で止まることがあります。Electron 本体には署名がなく、出たばかりの版には、まだ評判がないためです。そのときは、`npm install electron@45.2.3` のように版を指定して、少し前の版を入れ直します（45.3.4 は出た翌日に止められ、出てから2週間の 45.2.3 は動きました）。スマート アプリ コントロールを切るのは、おすすめしません。

上げたあとは、次の順に確かめます。

1. アプリのテスト（`npm test`）と、サーバーのテスト（「テスト」を参照）。
2. 画面を一通り使います。ログイン、仮のパスワードの変更、同意、会話（返事が少しずつ出る、声と口パク）、記憶（パスワードを変えたあとも読める）、設定、知らせ、管理者の画面、ログアウト、展示モード、`--cpu-only`。上げる前に保存した記憶が読めること、起動した端末に新しい警告やエラーが出ないことも見ます。
3. 通信を測ります。上げる前と後に、リポジトリのルートで次のスクリプトを動かしながら一通り使い、記録を比べます（`-Label` は、記録に付ける名前です）。つむぎ本体から PC の外への接続が0件で、増えた接続先がないことを確かめます。

   ```powershell
   pwsh -File tools/net-watch.ps1 -Label electron45
   ```

   見えるのは TCP だけで、読むのは約2秒ごとなので、短い接続は見落とすことがあります。そのため、4 も行います。

4. ファイアウォールで止めます。electron.exe から PC の外への通信を止める規則を一時的に作り、規則が効いていることを確かめてから、もう一度一通り使います。止める規則なので、PC の守りが弱くなることはありません。行き先から PC 自身（127 で始まるアドレスと `::1`）を除いているので、サーバー・Ollama・VOICEVOX にはつながります。

   規則は、リポジトリのルートで、管理者の PowerShell から作ります。

   ```powershell
   $exe = (Resolve-Path "tumugi_app\node_modules\electron\dist\electron.exe").Path
   New-NetFirewallRule -DisplayName "tumugi-test-block-outbound" -Direction Outbound -Action Block -Program $exe -RemoteAddress "0.0.0.0-126.255.255.255","128.0.0.0-255.255.255.255","::2-ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff"
   ```

   規則が効いているかは、ふだんの PowerShell（管理者の権限はいりません）で、リポジトリのルートから試します。electron.exe から example.com へ1回だけつなぎ、`blocked EACCES` と出れば止まっています。

   ```powershell
   $exe = (Resolve-Path "tumugi_app\node_modules\electron\dist\electron.exe").Path
   $env:ELECTRON_RUN_AS_NODE = "1"; & $exe -e "fetch('https://example.com').then(r => console.log('reached', r.status)).catch(e => console.log('blocked', e.cause ? e.cause.code : e.message))" | Out-Host; Remove-Item Env:ELECTRON_RUN_AS_NODE
   ```

   終わったら、管理者の PowerShell で規則を消します。

   ```powershell
   Remove-NetFirewallRule -DisplayName "tumugi-test-block-outbound"
   ```

設計と、45 に上げたときの結果は、`docs/superpowers/specs/2026-11-17-electron-upgrade-design.md` に書いています。

## セキュリティ上の前提

- サーバーには、この PC の中（127.0.0.1）からしか接続できません。同じネットワークのほかの PC からは接続できません。
- URL で公開されているのは `/api` だけです。
- API は、ブラウザで開いたほかのウェブページからは使えません。CORS の許しを返さず、Content-Type が `application/json` でない POST は、DB に触れる前に断ります（415）。アプリは、画面からではなく main プロセスから送るので、CORS は要りません。
- ログインは、同じ社員IDで15分のあいだに5回間違えると、しばらく（最大15分）止まります。パスワードの変更で今のパスワードを間違えた回も、同じ数に入ります。正しいパスワードで入ると（パスワードの変更で今のパスワードが合ったときも）、間違えた数は0に戻ります。
- 社員IDがないとき（退職した社員も）も、パスワードを確かめるのと同じ重さの計算をしてから断ります。エラーの文でも応答の速さでも、社員IDがあるかどうかは分かりません。
- ログインの記録（社員ID・時刻・成功したか）は、1日たつと消します。ロックに使うのは直近15分だけで、いつログインしたかの記録を長く残さないためです。
- 感情ログは、14日を過ぎると消します（集計に使うのは直近7日だけです）。同意画面にも書いています。消すのは、だれかがログインに成功するたびなので、だれもログインしないあいだは残ります。この版に替えたあとは、最初のログインで、それまでにたまった14日より前の記録も消えます。消えた記録は戻せません。
- 管理者の画面（ダッシュボード）に出るのは、10名以上のグループ単位の集計だけです。ただし、DB の感情ログは社員IDと結びついているので、サーバーを管理する担当者（サーバーの PC で Docker を操作できる人と、`.env` を読める人）は、社員ごとの記録を見られます。同意画面にも、そう書いています。実運用では、担当者を決めて社員に伝えます（「デモから実運用に切り替えるとき」）。
- ログアウトすると、サーバーに保存されているトークンも無効になります（サーバーに接続できないときは、期限の24時間まで残ります）。
- ログインの期限（24時間）が切れたときは、その回の返事や相談先の案内を出し終えてから知らせ、入力を止めます。ログイン画面へは、本人が知らせのボタンを押したときに移ります（案内が、勝手に画面から消えないように）。
- つむぎへの1回の発言は、1000文字までです。とても長い文を送ると、Ollama が、つむぎへの指示（人柄や決まり）まで黙って削ってしまうためです（2万文字の発言で確かめました）。超えているあいだは、残りの文字数と減らす数を出して、送信を止めます。書いた文は消しません。
- つむぎの記憶は、30項目・1項目100文字までです（記憶も、つむぎへの指示に入るため）。いっぱいのあいだは、新しいことを覚えません（今ある項目の上書きは続けます）。記憶の画面で、いらない項目を削除すると、また覚えます。
- 退職にした社員（`is_active = 0`）が持っているトークンは、使えなくなります。
- DB には、トークンそのものではなく、そのハッシュだけを保存しています。
- 社員の管理の操作は、そのたびにサーバーが「在籍している管理者か」を DB で確かめます。画面の出し分けは、見た目だけです。
- 仮のパスワードは、登録とリセットの応答で1回だけ返し、画面に1回だけ出します。DB にはそのハッシュだけを保存し、ログにも操作の記録にも書きません。仮のパスワードのままでは、パスワードの変更とログアウト以外のサーバーの機能を使えません。
- 管理者の操作（登録・修正・リセット・退職・在籍に戻す・削除）は、DB の `admin_audit_logs` に残ります。残すのは、操作した管理者の社員ID・操作・対象の社員ID・修正した項目の名前だけです。仮のパスワードも、変えた値も入れません。画面には出しません。管理者を作る道具（後述）の操作は、操作した管理者の欄が `CLI` になります。そのため、社員ID「CLI」は登録できません。
- 管理者は、自分自身を退職にする・消す・管理者から外す・リセットすることはできません。在籍している管理者が1人もいなくなる操作もできません。
- DB は、インターネットに出られない Docker の内部ネットワークに置いています。
- `.env` はリポジトリに含めません。
- 実運用ではデモデータを入れないよう、`.env` の `DEMO_SEED` を `false` にします（手順は「デモから実運用に切り替えるとき」）。`true` のままでも、デモ用ではない社員がいる DB には何もせず、`seed` が `Exited (1)` で止まります。
- 社員の気持ちを扱うため、データを外部のサービスに送らない方針です。Docker Desktop の AI アシスタント（Gordon）など、エラーや設定ファイルを外部に送る機能は使わないでください。
- Ollama にはサインインしないでください。サインインすると、インターネット上のサーバーで動く cloud モデル（名前が `-cloud` や `:cloud` で終わるもの）が使えるようになり、会話が PC の外に出ます。アプリは cloud モデルへの中継を拒否しますが、念のためです。

## デモから実運用に切り替えるとき

実在の社員を登録する前に、次の手順でデモデータを消してください。デモ用の社員や感情ログが残っていると、集計に混ざります。

1. サーバーを止めて、DB を消します（⚠️ DB の中身がすべて消えます）。

   ```bash
   docker compose --profile tools down -v
   ```

2. `.env` の `DEMO_SEED` を `false` にします。`DB_PASS` などのパスワードを変える場合は、DB を作り直すこのタイミングで変えてください。

3. サーバーを起動します。

   ```bash
   docker compose up -d
   ```

4. `seed` のログに「デモデータの投入をスキップしました」と出ていれば完了です。

   ```bash
   docker compose logs seed
   ```

5. 最初の管理者を作ります。デモの管理者（A001）も消えているので、サーバーのコンテナで、管理者を作る道具を動かします。この道具は、コマンドからだけ動きます（URL では開けません）。

   ```bash
   docker compose exec app php /var/www/tumugi/tools/admin_setup.php <社員ID> [名前] [部署]
   ```

   - 新しい社員IDのときは、名前と部署が必要です。付けないと、使い方が出て、何も作られません。名前や部署に空白が入るときは、引用符（`"`）で囲んでください。
   - 管理者が作られ、仮のパスワードが画面に1回だけ出ます。この表示は二度と出ないので、控えてください。
   - 道具の表示の日本語が化けるときは、先に `chcp 65001` を実行してください。

6. 仮のパスワードで、アプリにログインします。新しいパスワードを決める画面になるので、変えると、チャットに入れます。

7. サーバーを管理する担当者を決めます。サーバーの PC で Docker を操作できる人と、`.env` を読める人は、DB の感情ログを、社員IDごとに見られます（同意画面にも、そう書いています）。担当者を社内の規程に書き、社員に伝えてください。担当者でない人が、サーバーの PC にサインインしたり、`.env` を読んだりできないようにしてください。phpMyAdmin は、普段は起動しないでください。使ったときは、終わったら止めます（`docker compose --profile tools stop phpmyadmin`）。

8. 実在の社員は、管理者が、ダッシュボードの「社員」タブで登録します。登録のたびに、仮のパスワードが1回だけ出るので、本人に直接伝えてください。本人は、最初のログインで新しいパスワードに変えます。

## 管理者がパスワードを忘れたとき

ほかに在籍している管理者がいるときは、その管理者が「社員」タブでリセットします。ほかに管理者がいないときは、最初の管理者を作ったのと同じ道具でリセットします。

```bash
docker compose exec app php /var/www/tumugi/tools/admin_setup.php <社員ID>
```

すでにいる社員IDのときは、社員IDだけを指定します。名前や部署を付けると、道具は何も変えずに止まります（新しい社員を作るつもりで、すでにいる社員をリセットしてしまわないためです）。社員IDだけを指定すると、道具は、その社員を管理者・在籍にして、新しい仮のパスワードを画面に1回だけ出します。その社員のログインはすべて切れ、ログインの失敗の数も消えます。本人は、最初のログインで新しいパスワードに変えます。つむぎの記憶は読めなくなり、消えます（パスワードから鍵を作っているため）。

## 今ある DB に社員の管理を足すとき

社員の管理には、`employees` の新しい列（`must_change_password`）と、操作の記録の表（`admin_audit_logs`）が要ります。DB を新しく作る場合は、`schema.sql` にすでに入っているので、この手順は要りません。すでに動いている DB には、移行用の SQL を1回だけ流します。

**新しいコードを使う前に、流してください。** `tumugi_server/` は動いているコンテナにそのままつながっているので、コードを更新した時点で、ログインが新しい列を読みます。流すまでは、ログインに失敗します。

リポジトリのルートで、次のコマンドを実行します（PowerShell）。今いる社員は、そのまま使えます。

```powershell
Get-Content -Raw -Encoding utf8 tumugi_server/sql/migrations/2026-10-26-employee-management.sql | docker compose exec -T db sh -c 'mysql --default-character-set=utf8mb4 -uroot -p$MYSQL_ROOT_PASSWORD $MYSQL_DATABASE'
```

2回目に流すと、"Duplicate column" で止まります。それは「もう済んでいる」という意味なので、そのままで構いません。

## 今ある DB に、最低人数の守りの修正を足すとき

集計を「記録した時点の所属」で作り、待ちの7日も記録した時点で決めるために、社員の新しい列（`counted_from`：集計に入れ始める時刻）、`emotion_logs` の新しい列（`department`・`is_new_grad`・`is_counted`）と、本人あての知らせの表（`employee_notices`）が要ります。DB を新しく作る場合は、`schema.sql` にすでに入っているので、この手順は要りません。すでに動いている DB には、移行用の SQL を1回だけ流します。今までの記録には、その社員の今の所属が写されます。今いる社員の `counted_from` は、登録の時刻になります。今の管理者の記録は、集計に入らない記録になります。

**社員がアプリを使っていない時間に、コードの更新とあわせて、続けて流してください。** `tumugi_server/` は動いているコンテナにそのままつながっているので、コードを更新した時点で新しいコードが動きます。流すまでのあいだは、感情ログの保存、集計、パスワードの変更（新しい社員の最初のログインを含む）、社員の修正（部署・新卒・管理者の権限）・在籍に戻す・パスワードのリセットが失敗します（その間の感情ログは残りません）。逆に、古いコードのまま流すと、古いコードの感情ログの保存が失敗します。

流す前に、DB の控えを取っておくと安心です（移行は、全部の感情ログを書きかえます）。リポジトリのルートで実行します（PowerShell）。

```powershell
docker compose exec -T db sh -c 'mysqldump --default-character-set=utf8mb4 --single-transaction -uroot -p$MYSQL_ROOT_PASSWORD $MYSQL_DATABASE --result-file=/tmp/tumugi-backup.sql'
docker compose cp db:/tmp/tumugi-backup.sql ./tumugi-backup.sql
```

控えのファイルには、感情ログと、社員の氏名・パスワードのハッシュが入っています。Git に入れないでください（`.gitignore` で除いています）。使い終わったら、手元のファイルと、コンテナの中の控え（`docker compose exec db rm /tmp/tumugi-backup.sql`）を消してください。

控えを取ったら、次のコマンドで移行を流します（PowerShell）。

```powershell
Get-Content -Raw -Encoding utf8 tumugi_server/sql/migrations/2026-11-13-b1-min-size.sql | docker compose exec -T db sh -c 'mysql --default-character-set=utf8mb4 -uroot -p$MYSQL_ROOT_PASSWORD $MYSQL_DATABASE'
```

2回目に流すと、"Duplicate column" で止まります。ただし、これは「もう済んでいる」とは限りません。途中で止まったときも、2回目は最初の文で同じエラーになります。済んでいるかどうかは、移行 SQL の先頭のコメントに書いてある見分け方で確かめてください。途中で止まっていたときは、SQL ファイルの、止まった所から後ろの文を、手で流してください。

移行のあと、今いる社員は、登録から7日たっていれば、そのまま集計に入ります。移行の前の記録のうち、その社員の登録から7日以内のものは、集計に入らなくなります。管理者の記録も、集計に入らなくなります。そのため、移行の直後に、集計が1回変わることがあります。

仮のパスワードを自分のパスワードに変えてから7日間の記録は、集計に入りません（あとからも入りません）。そのため、次のときは、最初の7日間、その社員の分が入らず、人数が足りなければ集計が出ません。

- 初めて導入した会社（社員が最初のログインでパスワードを決めてから7日間）
- 移行の直前に登録した社員（登録から7日たつまで、その社員の記録は集計に入りません。まだパスワードを決めていない社員は、決めてから7日です）

デモの DB は、社員を入れてから7日以上たっていれば、そのまま集計が出ます。そうでなければ、作り直してください（`docker compose --profile tools down -v` のあと `docker compose up -d`。DB の中身はすべて消えます）。

部署を移った人は、直近7日のあいだ、前の部署と新しい部署の両方で、1人と数えられます。

## うまく動かないとき

- **ポート 8080 / 8081 がすでに使われている**：使っているアプリを止めてください。ポートを変える場合は、`compose.yaml` と `tumugi_app/net-policy.js` の `BASE_URLS` の両方を変更する必要があります。
- **`npm start` が `Error: spawn UNKNOWN` で止まる**：Windows のスマート アプリ コントロールが、Electron 本体を止めていることがあります。イベント ビューアーの「アプリケーションとサービス ログ > Microsoft > Windows > CodeIntegrity > Operational」に、electron.exe を止めた記録があれば、そうです。少し前の版の Electron を入れ直してください（「Electron の版を上げるとき」を参照）。
- **つむぎが「AIのモデル（gemma4:e4b）が入っていないみたい」と言う**：Ollama に、使うモデルが入っていません。`ollama pull gemma4:e4b` を実行してください（最初の1回だけ、インターネット接続が必要です）。入れ終われば、アプリを開き直さなくても、次の発言から話せます。
- **テーブル構造（`tumugi_server/sql/schema.sql`）を変えたのに反映されない**：構造は DB を初めて作るときにだけ読み込まれます。`docker compose --profile tools down -v` のあと、もう一度 `docker compose up -d` を実行してください（⚠️ DB の中身がすべて消えます。実運用の DB では実行しないでください。社員の管理のための変更は、消さずに足せます。「今ある DB に社員の管理を足すとき」を参照）。
- **`seed` が `Exited (1)` で止まる（「デモ用ではない社員が…」と出る）**：デモの DB に、デモ用ではない社員（「社員」タブや管理者を作る道具で足した社員）がいます。試しに足した社員は、「社員」タブで退職にしてから「削除」で消し、`docker compose up -d` をもう一度実行してください。実運用の DB で出たときは、`.env` の `DEMO_SEED` を `false` にしてください。
- **確かめ用に足した社員を、「削除」しようとすると断られる（「直近7日間に感情記録がある社員は削除できません」）**：その社員に、直近7日間の感情の記録があります。最後の記録から7日たつと消せます。デモの DB なら、`docker compose --profile tools down -v` のあと `docker compose up -d` で作り直せます（⚠️ DB の中身がすべて消えます）。確かめるときは、同意の画面で「送信しない」を選ぶと、記録が残りません。
- **パスワードをリセットした社員の記録が、集計に入らない**：リセットのあと、社員が新しいパスワードを決めてから7日間は、その社員の記録は集計に入りません（あとからも入りません）。10名ちょうどの部署では、その間、部署の集計が出なくなることがあります。
- **`docker compose` で「.env がありません」と表示される**：手順1の `.env` を作ってください。
- **`.env` の `DB_PASS` などを変えたら、DB に接続できなくなった**：DB のパスワードは、DB を初めて作るときにだけ設定されます。デモ環境なら `docker compose --profile tools down -v` で DB を作り直してください（DB の中身はすべて消えます）。
- **発言しても感情ログが記録されない**：アプリの「設定」で「現在、感情記録を送信しています」になっているか確認してください。同意は PC ごと・社員ごとに保存されます。
- **mysql の結果で日本語が `???` になる**：`--default-character-set=utf8mb4` を付けてください（「よく使うコマンド」の書き方）。
- **phpMyAdmin を起動すると「network ... not found」と表示される**：DB を作り直す前の古い phpMyAdmin が残っています。`docker compose --profile tools up -d --force-recreate --no-deps phpmyadmin` で作り直してください。

## 立ち絵について

- 立ち絵の画像は、このリポジトリに入っていません（`tumugi_app/images/*.png` は Git の管理外です）。
- 立ち絵は、坂本アヒルさんの「春日部つむぎ立ち絵素材」です。まばたき・口パク用の絵も含めて、絵はすべて坂本アヒルさんのものです（素材に入っている目や口の差分を、表情ごとに組み合わせて書き出しました）。素材の再配布になるため、画像はこのリポジトリに入れていません。
- アプリは `tumugi_app/images/` の次のファイルを読みます。表情は `normal`・`happy`・`sad`・`angry`・`surprised`・`troubled` の6つです。

| ファイル | 使いどころ |
|---|---|
| `<表情>_open.png` | 元の絵 |
| `<表情>_close.png` | まばたき |
| `<表情>_talk.png` | 口パク（口だけが元の絵と反対の絵）。なければ口パクしません |
