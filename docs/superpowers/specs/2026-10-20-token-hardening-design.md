# トークンの問題 設計書

- 日付：2026-10-20
- 状態：実装済み（2026-10-26。5919004・87805a6・324b229）。設計は 2026-10-20 にユーザーが範囲と形を承認した

## 1. 背景と目的

### 背景
- 2026-10-07 のレビューで見つかった「トークンの問題」（期限のずれ、ログアウトしても無効にならない、退職者を見ていない）が、まだ残っている。
- 実際に会社で使うには、ログアウトや退職で、ログインがきちんと切れる必要がある。

### 目的
- ログアウトしたら、サーバーのトークンも使えなくする。
- 退職にした社員（`is_active = 0`）のトークンは、その時点で使えなくする。
- 期限を、サーバーとアプリの時計のずれに左右されない形にする。
- DB を見られる人が、社員になりすませないようにする。

### 成功基準
- ログアウトすると、DB からその PC のトークンが消える。
- 退職にした社員は、次にサーバーに送ったときに 401 になり、ログアウトされる。
- 期限は MySQL で計算し、アプリはサーバーから受け取った「残りの秒数」をもとに判断する。
- 期限の切れたトークンが、DB にたまり続けない。
- DB には、トークンそのものではなく、ハッシュだけが入っている。
- `npm test` がすべて通る。

## 2. 決定事項（2026-10-20 にユーザーと合意したもの）

1. 範囲は「3つ＋掃除＋ハッシュ」。3つは、ログアウトで無効にする、退職者を止める、期限を SQL で計算する。これに、期限切れのトークンの掃除と、トークンをハッシュで保存することを足す。
2. アプリは、トークンの期限を「残りの秒数」（`expires_in`）で受け取る。ログインした瞬間の PC の時計に足して、期限として保存する。
3. サーバー側の形（4.1）をユーザーが承認した。
4. アプリ側の形と確かめ方（4.2・4.3）をユーザーが承認した。

## 3. 調べて分かったこと（2026-10-20）

- **ログアウト**：アプリの `logout()`（`js/auth.js`）は、アプリに保存したトークンを消して、ログイン画面に移るだけ。サーバーのトークンは、期限（24時間）まで使える。
- **退職者**：`verifyToken()`（`includes/db.php`）は `auth_tokens` だけを見る。`is_active` は見ていない。
  - `save_emotion.php` は `verifyToken()` だけなので、退職者のトークンでも感情ログを送れる。
  - `dashboard_data.php` と `change_password.php` は、それぞれ自分で `is_active` を見ている。
  - `login.php` は `is_active = 1` の社員しかログインさせない。
- **期限**
  - `login.php` は PHP で期限を計算し（`date('Y-m-d H:i:s', strtotime('+24 hours'))`）、`verifyToken()` は MySQL の `NOW()` で比べる。
  - 今は PHP（`date.timezone = Asia/Tokyo`）と MySQL（`--default-time-zone=+09:00`）がそろっているので、ずれは起きていない。それでも、2つの時計を使う作りは残っている。
  - アプリは、受け取った `expires_at`（`"2026-10-21 14:00:00"` の形、タイムゾーンなし）を PC の時計と比べている（`getStoredToken()`）。社内サーバーと PC の時計やタイムゾーンがずれると、判断がずれる。
- **掃除**：期限の切れたトークンを消す処理がない。
- **保存の形**：`auth_tokens.token`（`VARCHAR(64)`）に、トークン（`bin2hex(random_bytes(32))` の64文字）をそのまま保存している。phpMyAdmin などで DB を見られる人なら、そのトークンを使って社員になりすませる。
- **ログアウトを呼ぶところ**：`logout()` は、ログアウトのボタンのほか、401 を受けたとき（`script.js` の `sendEmotionLog`・`changePassword`、`admin-dashboard.js`）にも呼ばれる。
- **中継の許可リスト**：server は4組、全体で9組。テスト（`test/net-policy.test.js`）は、`POST /logout.php` を「許可していない例」として使っている。
- **テスト**：今は88個。PHP には自動のテストがない。

## 4. 設計

### 4.1 サーバー

**`tumugi_server/includes/db.php`**
- `hashToken(string $token): string` を足す。`hash('sha256', $token)`（64文字の16進）を返す。
  - トークンは32バイトのランダムな値なので、ソルトは要らない（総当たりや表引きで元に戻せない）。
- `verifyToken()` を直す。
  - `getBearerToken()` で受け取ったトークンを `hashToken()` にしてから比べる。
  - `employees` と結びつけ、`is_active = 1` の社員のトークンだけを通す。

  ```sql
  SELECT t.employee_id FROM auth_tokens t
  JOIN employees e ON e.id = t.employee_id
  WHERE t.token = :token AND t.expires_at > NOW() AND e.is_active = 1
  ```

**`tumugi_server/api/login.php`**
- 定数 `TOKEN_TTL_HOURS = 24` を置く（24時間は今と同じ。Claude の判断）。
- パスワードが合ったあと、次の順に行う。
  1. 期限の切れたトークンを、全員分消す（`DELETE FROM auth_tokens WHERE expires_at <= NOW()`）。
  2. トークンを今と同じく作り（`bin2hex(random_bytes(32))`）、DB には `hashToken()` の値を入れる。
  3. 期限は MySQL で計算する（`NOW() + INTERVAL 24 HOUR`。定数は SQL に埋め込む。`login_guard.php` の `LOCKOUT_WINDOW_MINUTES` と同じ書き方）。
- 応答は、`expires_at` のかわりに `expires_in`（`TOKEN_TTL_HOURS * 3600` = 86400。整数の秒数）を返す。ほかの項目（`token`・`employee_id`・`department`・`is_admin`）は今と同じ。

**`tumugi_server/api/logout.php`（新しく作る）**

| 順 | 確かめること | 止まったときの応答 |
|---|---|---|
| 1 | POST か | 405「POSTメソッドのみ許可されています」 |
| 2 | `Authorization: Bearer <token>` があるか（`getBearerToken()`） | 400「トークンがありません」 |

- `DELETE FROM auth_tokens WHERE token = :token`（`hashToken()` の値）を行い、200 で `{"status":"ok"}` を返す。
- 消す行がなくても（期限切れ・すでに消えている・退職者）200 を返す。`verifyToken()` は使わない。消せなくて困ることはなく、トークンを持っている人が自分で無効にするだけなので（Claude の判断）。

**`tumugi_server/api/change_password.php`**
- 「今のトークン以外を消す」の比べ方を、`hashToken($currentToken)` にする。ほかは変えない。

**`tumugi_server/sql/schema.sql`**
- 構造は変えない。`token` の列に、トークンの SHA-256（16進64文字）を入れることを、説明として書く（Claude の判断）。

**入れ替えるときの影響**
- 今 DB にあるトークン（ハッシュにしていない値）は、どれも合わなくなる。ログインしている人は、次にサーバーに送ったときに 401 になり、一度だけログインし直しになる。
- 古い行は、期限が切れたあと、次のログインのときに消える。

### 4.2 アプリ

**`tumugi_app/net-policy.js`**
- server に `{ method: "POST", path: "/logout.php" }` を足す（全体で10組）。
- テストを直す。
  - 「許可した9つの組」を「10の組」にし、`["server", "/logout.php", "POST", "http://127.0.0.1:8080/api/logout.php"]` を足す。
  - 「許可していないエンドポイント」の例から `["server", "/logout.php", "POST"]` を外す。
  - 「メソッドが違えば拒否する」に `["server", "/logout.php", "GET"]` を足す。

**`tumugi_app/js/auth.js`**
- `submitLogin()`
  - 応答の `expires_in` が正の数でなければ（ない・数でない・0以下）、ログインを失敗として扱い、「ログインに失敗しました」と出してボタンを元に戻す。何も保存しない（Claude の判断）。
  - 期限は `new Date(Date.now() + data.expires_in * 1000).toISOString()` を `AUTH_EXPIRES_KEY` に保存する。
- `getStoredToken()` は変えない。保存した期限（ISO の形）と PC の時計を比べるので、どちらも同じ PC の時計になり、サーバーとのずれは影響しない。
- `logout()`
  - 保存しているトークンがあれば、`POST /logout.php`（トークン付き）を送る。**返事は待たない**（Claude の判断）。
    - 中継（`net:serverRequest`）は main.js で動くので、画面がログイン画面に切り替わっても、送信は最後まで続く。
    - サーバーが落ちていても、ログアウトはすぐ終わる。その場合、トークンは期限まで残る（受け入れる）。
  - そのあとは今と同じ（`clearAuth()` と `window.electronAPI.logout()`）。
  - 401 を受けてログアウトするときも同じく送る。サーバーで消す行がないだけで、害はない。
- `requireAuthOrRedirect()`（起動したときに期限切れならログイン画面に戻す）は変えない。期限切れのトークンはサーバーでも使えないので、`logout.php` は送らない。

**画面**：変えない。

**`README.md`**：「セキュリティ上の前提」に次を足す（Claude の判断）。
- ログアウトすると、サーバーのトークンも無効になる。
- 退職にした社員（`is_active = 0`）は、持っているトークンも使えなくなる。
- DB には、トークンのハッシュだけを保存している。

### 4.3 確認の手順（ユーザーが行う。E048 を使う）
1. `npm test` がすべて通る（88個のまま。net-policy のテストは数が変わらない）。
2. 変えた PHP（`login.php`・`logout.php`・`db.php`・`change_password.php`）に、文法の誤りがない（`php -l`）。
3. **入れ替え**：入れ替える前からログインしていたアプリは、次にサーバーに送ったときに 401 でログアウトされる（古いトークンが合わなくなったことの確認）。
4. **ログイン**：E048 でログインできる。会話して、感情ログが送れる（新しいトークンのハッシュが DB と合うことの確認）。
5. **ログアウト**：ログアウトすると、DB の E048 のトークンが1つ減る。
6. **期限**：DB で E048 のトークンの期限を過去にすると、次の送信で 401 になり、ログアウトされる。次にログインすると、期限の切れた行が消えている。
7. **退職者**：DB で E048 を `is_active = 0` にすると、次の送信で 401 になり、ログアウトされる。ログインもできない。確かめたら `is_active = 1` に戻し、ログインで記録された失敗を `login_attempts` から消す。
8. **展示モード**（`npm start -- --exhibit`）でも、ログアウトでトークンが消える。

## 5. 範囲外
- ログアウトせずにアプリを閉じたときの失効（トークンは期限まで残る）。
- 使っているあいだ期限が延びる仕組み。
- 社員の登録・管理者によるリセット・退職者を設定する画面（社員の管理として、別に作る）。
- `login_attempts` の掃除（たまり続ける）。
- CORS の見直し、HTTPS 化。

## 6. リスクと対策
- **入れ替えると、全員が一度ログインし直しになる**：意図どおり。展示やデモの前日には入れ替えない。
- **ログアウトで返事を待たないので、サーバーが落ちているとトークンが残る**：期限（24時間）で切れる。ログアウトを止めて待たせるより、すぐ終わるほうを選んだ。
- **退職者の確認で E048 を止める**：確かめたら必ず `is_active = 1` に戻す（4.3 の7）。
