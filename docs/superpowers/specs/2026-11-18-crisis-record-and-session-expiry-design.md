# キーワードの回の記録の確かめと、ログインの期限切れの扱い 設計書

- 日付：2026-11-18
- 出どころ：全コードのレビュー（2026-11-11）の次の2つ
  - A1「危機のキーワードの誤検知が、そのまま『危機』として記録される」
  - A11「トークンの期限（24時間）が切れると、返事や危機の案内の途中でログイン画面に戻る」
- 2つとも、感情ログを送る所（`tumugi_app/js/script.js` の `sendEmotionLog` と、それを呼ぶ `handleUserInput`）を直すので、1つの設計書にまとめる。

## 1. 問題

### A11 期限切れで、返事や危機の案内の途中に画面が切り替わる

- 感情ログを送る関数（`sendEmotionLog`）は、同意を見るより先に、ログインの期限を見る（期限は、この PC の時計で数える）。
  - 切れていれば、すぐログアウトし、画面ごとログイン画面に入れ替える。
  - サーバーが 401 を返したときも同じ。
- 感情ログは、返事を出しはじめる前に、待たずに送る。
  - そのため、期限が切れたあとの最初の発言で、返事を出している途中に画面が切り替わり、会話が消える。
  - 同意していない社員でも起きる。
- 危機のキーワードに当たった回も同じ。相談先の案内を出した直後に画面が切り替わり、案内（電話番号）が画面から消える。

### A1 キーワードの誤検知が、そのまま危機として記録される

- キーワードは、空白を取ってから部分一致で調べる。そのため、危機ではない文でも当たる。
  - 「不安が消えたいい一日だった」（「消えた」＋「い」）
  - 「鍵をさがしにたいへん苦労した」（「…しに」＋「たい」）
  - 「自殺防止の研修を受けた」「練炭で焼き肉をした」（語がそのまま入っている）
- 当たると、相談先を案内したうえで、感情ログに危機として送る。
  - サーバーは、点数100で記録する。
  - 同意している社員なら、部署の平均が上がる。
  - 部署に「危機あり」が出る（直近7日に記録のある在籍社員が10名以上の部署）。
- 誤検知や冗談で「危機あり」が出つづけると、管理者が「危機あり」を信用しなくなるおそれがある。そうなると、本当の危機のときに効かなくなる。

## 2. ねらいと、やらないこと

**ねらい**

- ログインの期限が切れても、その回の返事や危機の案内は最後まで出す。画面は勝手に切り替えない。
- キーワードに当たった回は、判定の呼び出し（`classifySafety`）で確かめてから記録する。
- 相談先の案内は、今までどおり、キーワードに当たったらすぐ出す。

**やらないこと**

- 次のものは変えない。
  - キーワードの一覧と、照合のしかた。
  - 判定の指示（`CLASSIFY_INSTRUCTION`）。指示を変えると、測り直しになる。
  - 「⚠️ ログ送信失敗」の文。つむぎの発言の中の記号は、あとで決める。
  - ログインの期限の長さ（24時間）。
- お知らせの「確認」とパスワードの変更で、期限切れや 401 に当たったときは、今までどおりすぐログイン画面へ移る。本人がボタンを押した操作のため。

**こうなったら失敗**

- 本当の危機の回が、記録から消える。判定に失敗した回や、答えが読めない回も含む。
- 相談先の案内が遅れる。または、本人がボタンを押さないのに、案内が画面から消える。
- 期限が切れたのに、入力できるままになる。

## 3. 測ったこと（2026-11-18）

キーワードに当たる文を、アプリと同じ判定に通した。

- 判定の条件は、アプリと同じにした。
  - 指示・スキーマ・設定はアプリと同じ。
  - モデルは gemma4:e4b、temperature は 0。
  - 判定に渡す会話は `js/conversation.js` で組み立てた。
- 会話の流れは2つ。
  - ログインのあいさつ（夕方）のあと。
  - あいさつと、雑談の1往復のあと（「今日は会議が三つもあって、ちょっと疲れた」）。
- 1文を、流れごとに3回ずつ判定した（1文あたり6回）。GPU で動かした。
- 結果
  - 300回すべて、答えを JSON として読めた。
  - 判定の時間は、中央値2.9秒だった。
- 測定のスクリプトは、リポジトリに入れていない（`.superpowers/spike-llm/keyword-judge.mjs`）。

## 4. ユーザーが決めたこと

**A11**

1. 回を終えてから知らせる。
   - その回の返事や危機の案内は、最後まで出す。その回の感情ログは送らない。
   - 回が終わったら知らせを出し、入力を止める。
   - ログイン画面へは、本人が知らせのボタンを押したときだけ移る。危機の案内が、勝手に消えないようにするため。
   - サーバーが 401 を返したときも同じ。
2. 知らせは、入力の所に出す。
   - 話題の例・入力欄・送信の代わりに、知らせの文と「ログイン画面へ」のボタンを出す。
   - 会話の欄には重ねない。

**A1**

3. 先に測ってから決める。
   - 前もって、次のように決めておいた。本当の危機を1つも見逃さなければ (a)。見逃せば (b)（間違えやすい語だけ確かめる）。
   - 見逃しは0だったので、(a) にした。キーワードに当たった回は、すべて判定で確かめてから記録する。
4. 大げさな言い方も、ほかと同じく判定に任せる。判定が危機ではないと答えれば、記録しない。
   - キーワードに当たらない発言には、もう同じ決まりが効いている（「（笑）」がついた冗談や、明らかに大げさな言い方は危機ではない。迷ったら危機）。
5. 判定が「危機ではない」と答えても、ハラスメントがあれば記録する（危機として。ハラスメントの種類も入れる）。
   - キーワードに当たらない軽い言い方は、今もハラスメントとして記録される。
   - ここで記録しないと、「自殺しろと言われた」のような重い言い方のほうが、記録から消えてしまう。

## 5. まとめ役が決めたこと（違えば直す）

- 判定の呼び出しに失敗した回と、答えが読めない回は、危機として記録する（ハラスメントは「なし」）。
  - 今の答えの読み方（`parseClassification`）は、読めない答えを「危機ではない」にする。
  - そこで、crisis の値が読めたかも返すようにする。
- 判定が危機と答えた回も、判定のハラスメントの種類を送る。
  - 今は、キーワードの回はいつも「なし」で送っている。
  - キーワードに当たらない回の危機と、同じ扱いになる。
- 感情は、今までどおり sad として送る。危機のときは、感情に関係なく、サーバーが点数を100にする。
- 判定を待つあいだも、入力は止めない。
  - 案内を出し終えたら、今までどおり入力を戻す。
  - 記録は、案内を出し終えて、判定の答えもそろってから送る。今も、案内を出し終えてから送っている。
  - この順番は変えない。案内の途中に「ログ送信失敗」の吹き出しが割りこまないようにするため。
- 記録しないと決めた回は、console にそう出す。発言の中身と判定の理由は出さない（今の決まりのとおり）。
- 同意していない社員でも、キーワードの回の判定は行う。
  - 処理は分けない。
  - 記録は、今までどおり同意を見て、送らない。
- 期限切れの知らせが出ているあいだ、左の欄の状態は「ログインを待っています」にする。「話を聞いています」のままだと、入力できるように見えるため。
- 知らせの文とボタン
  - 文：「ログインの期限が切れました。続けるには、もう一度ログインしてください。」と「ログイン画面に移ると、この画面の会話は消えます。」
  - ボタン：「ログイン画面へ」。今のログアウトのボタンと同じ処理にする。
- 知らせを出したら、「ログイン画面へ」にフォーカスを移す。入力欄が消えて、フォーカスの行き先がなくなるため。
- README の2か所に、1文ずつ書き足す。
  - 「見逃しを減らす」の行：キーワードの回の記録は、判定で確かめること。
  - 「セキュリティ上の前提」：期限が切れたときの動き。
- 作業は小さいので、エージェントは使わず、まとめ役が直して、ユーザーが確かめる。計画書は作らず、6章の順に直す。

## 6. 設計

### 6.1 判定の答えを読む（`js/safety.js` の `parseClassification`）

- 戻り値に `readable` を足す。答えから crisis の値（true か false）が読めたかを表す。

| 答え | readable |
|---|---|
| JSON として読めて、crisis が true か false | true |
| JSON が途中で切れていても、`"crisis": true` か `"crisis": false` が見える | true |
| それ以外（空・読めない・crisis が文字列の "true" など） | false |

- crisis と harassment の読み方は変えない。
- `classifySafety` は、今までどおり `{ ok: true, ...parseClassification(…) }` を返す（readable も入る）。キーワードに当たらない回は、readable を使わない。

### 6.2 キーワードの回の記録を決める（`js/safety.js` に `keywordTurnRecord` を足す）

- 判定の答えから、記録するかを決める。答えは `classifySafety` の戻り値（`{ ok, readable, crisis, harassment }`）。
- 画面に触らない関数にして、テストする。

| 判定の答え | 記録 | 送るハラスメント |
|---|---|---|
| 呼び出しに失敗した（ok が true でない）・答えが読めない（readable が true でない）・答えがない | 危機として送る | none |
| 危機 | 危機として送る | 判定の答え |
| 危機ではない・ハラスメントあり（received・said） | 危機として送る | 判定の答え |
| 危機ではない・ハラスメントなし | 送らない | — |

- 戻り値
  - 送るとき：`{ send: true, harassment }`
  - 送らないとき：`{ send: false }`
- ハラスメントが決まった値（none・received・said）でないときは、none として扱う。

### 6.3 キーワードの回の流れ（`js/script.js` の `handleUserInput`）

1. 表情を troubled にする（今までどおり）。
2. 判定（`classifySafety`）を始める。待たない。
   - 案内を会話の履歴に足す前に始める。
   - 判定に送る会話は、呼んだ時点で組み立てる。なので、今回の案内は判定に入らない（入れると、同じ発言が判定に2回入る）。
3. 案内を出す（`showCrisisSupportMessages`。今までどおり）。
4. 判定の答えを待って、`keywordTurnRecord` で決める。送るときは `sendEmotionLog("sad", true, harassment)`。
   - 答えを待つ処理は、待たずに進める。入力を戻すのを遅らせないため。
5. 入力を戻す（今までどおり）。

Ollama で動く処理が1つ増える。

- Ollama は、判定・返事の整え・判定の整えの順に受け取る。
- CPU だけの PC では、今も、案内の声を作るあいだに整えが同時に動いている。判定が1つ増えるので、Ollama が働く時間が長くなる。声の遅れが大きく変わるかは、測っていない。
- 案内のすぐあとに次の発言をすると、その回の判定と返事は、この判定のあとになる。

### 6.4 期限切れ（`js/script.js`）

- 新しい状態 `sessionExpired`（はじめは false）。
- `sendEmotionLog`：次のときは、`logout()` ではなく `markSessionExpired()` を呼んで終わる。その回の感情ログは送らない。
  - トークンがないとき（期限切れを含む）。
  - サーバーが 401 を返したとき。
- `markSessionExpired()`：`sessionExpired` を true にする。
  - 回の途中（`turnInProgress`）でなければ、すぐ知らせを出す。
  - 回の途中なら、ここでは出さない。
- `handleUserInput` の終わり（finally）：今の処理のあと、`sessionExpired` なら知らせを出す。
  - 回は、声を読み終えるまで続く。なので、知らせは声のあとに出る。
- キーワードの回は、記録を、回の終わりより後に送ることがある。
  - そのとき期限切れに気づけば、すぐ知らせを出す。
  - 次の回が始まっていれば、その回の終わりに出す。
- `setButtonBusy`：`sessionExpired` のあいだは、入力欄・送信・話題の例を押せないままにする。
- `sendTextInput`：`sessionExpired` なら何もしない（念のため）。
- 知らせを出す関数
  - 入力の所に印（class `expired`）を付けて、話題の例・入力の行・ヒントを隠し、知らせを出す。
  - 状態の表示を直し、「ログイン画面へ」にフォーカスを移す。
  - 2回目からは何もしない。
- 「ログイン画面へ」：`logoutAndClearNotices`（ログアウトのボタンと同じ）。`CLICK_HANDLERS` に足す。

### 6.5 画面（`index.html`・`css/style.css`・`js/chat-view.js`）

- `index.html`：`.compose` の中の先頭に、知らせを置く。
  - id は `sessionExpired`。`hidden` と `role="alert"` を付ける。
  - 中身は、文2つと「ログイン画面へ」のボタン（id `sessionExpiredBtn`、class `btn small`）。
- `css/style.css`
  - 知らせは、お知らせと同じく、左に青い線を付ける。
  - `.compose.expired` のとき、話題の例・入力の行・ヒントを隠す。
- `js/chat-view.js` の `statusText`
  - `expired` が true なら「ログインを待っています」。
  - 話しているときは、今までどおり「話しています」を先にする。

10. （401 の確かめ）
    - もう一度ログインし、設定で感情ログを「送る」にする。
    - console で次を実行してから、「今日は疲れた」を送る。返事のあとに知らせが出る（サーバーが断るので、記録は残らない）。

      ```js
      await window.electronAPI.storeSet("auth_token", "x")
      ```

    - 「ログイン画面へ」を押し、もう一度ログインして、すぐ感情ログを「送らない」に戻す。
11. 終わったら、片づける。
    - T901 を退職にしてから消す。
    - `main.js` の openDevTools の行を、コメントに戻す。

## 8. 心配な点と、戻し方

- 判定が本当の危機を「危機ではない・ハラスメントなし」と答えると、その回は記録されない（案内は出る）。3章の限界のとおり、測った文と流れは限られる。
- 「痛みが消えたいまは元気」のように、判定も読みちがえる文は、今までどおり危機として記録される。
- 判定が危機ではないと答えても、ハラスメントがあれば、危機として記録する。
  - そのため、部署に「危機あり」が出る。
  - 「言ってしまった」側も、危機として記録される。
  - どちらも、今と同じ。
- キーワードの回の記録は、案内を出し終えて判定もそろってから送る。CPU だけの PC で判定が遅いと、次の回の途中に「⚠️ ログ送信失敗」が出ることがある（サーバーにつながらないときだけ）。
- 判定の答えを待っているあいだにアプリを閉じると、その回は記録されない。今も、案内を出し終える前に閉じると、記録されない。
- お知らせの「確認」を、回の途中に押して期限切れに当たると、今までどおり、すぐログイン画面へ移る（2章のやらないこと）。
- 戻し方：コミットを戻せば元どおりになる。保存の形も、サーバーも変えない。
