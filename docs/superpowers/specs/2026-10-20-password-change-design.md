# パスワード変更 設計書

- 日付：2026-10-20
- 状態：実装済み（2026-10-20。dd55436・3c70005）。設計は 2026-10-16 にユーザーが承認し、2026-10-20 に今のコードと突き合わせて書面にした

## 1. 背景と目的

### 背景
- 実際に会社で使うとき、社員が自分でパスワードを変えられる必要がある。
- `tumugi_server/api/change_password.php` は前からあるが、アプリからは使っておらず、中継の許可リスト（`net-policy.js`）にも入っていない。直すべき点もある（3. を参照）。
- つむぎの記憶は、社員のパスワードから作った鍵で暗号化している（`memory-crypto.js`）。パスワードを変えたら、記憶の鍵も新しいパスワードのものに付け替える必要がある。付け替えないと、次のログインで記憶が読めず、消えてしまう。

### 目的
- 社員が、好きなときにアプリの「設定」からパスワードを変えられるようにする。最初のログインでの強制はしない。

### 成功基準
- 「設定」からパスワードを変えられる。変えたあとは、新しいパスワードでログインでき、古いパスワードではできない。
- 変えたあとも、つむぎの記憶が残っている。
- 変えると、ほかの PC でのログイン（トークン）が切れる。今の PC のログインは続く。
- 今のパスワードを間違えると、理由が出て、ログアウトはしない。15分に5回間違えると止まる（ログインも止まる）。
- 展示モードでは、パスワードの変更欄が出ない。
- `npm test` がすべて通る。

## 2. 決定事項（2026-10-16 にユーザーと合意したもの）

1. 実際に会社で使うときのための機能。社員がいつでも変えられるだけで、最初のログインでの強制はしない。
2. 社員の登録、管理者によるリセット、退職者のログイン停止は、今回はしない（別に作る）。
3. 今のパスワードを間違えたときは、ログアウトさせない（401 ではなく 403 で返す）。
4. 試せる回数は、ログインと共通にする（15分に5回）。
5. 変えたら、ほかのトークンを消す（ほかの PC のログインを切る）。
6. 記憶の鍵の付け替えは、サーバーでの変更が成功した**あと**に行う。逆にすると、サーバーで失敗したときに記憶が読めなくなる。
7. 「プライバシー設定」を「設定」に改め、そこに「パスワードの変更」欄を足す。展示モードでは欄を隠す。
8. 確かめるときは E048 を使う（展示で使う E001 などは変えない）。最後に元のパスワードに戻す。

## 3. 調べて分かったこと（2026-10-20）

- **今の `change_password.php` の問題**
  1. 8文字以上かを `strlen`（バイト数）で数えている。全角だと3文字で通ってしまう。
  2. bcrypt は72バイトを超えた分を無視するのに、上限を見ていない。
  3. 今のパスワードが違うと 401 を返す。アプリは 401 を「ログインが切れた」と見なしてログアウトする（`script.js` の `sendEmotionLog` と同じ扱い）。
  4. 試せる回数の制限がない。
  5. 変えても、ほかのトークンが残る。
  6. 在籍しているか（`is_active`）を見ていない。
- **試した回数の記録**：`login_attempts` は社員ID（`employee_code`）で数える。`change_password.php` はトークンから数字の id しか分からないので、id から社員IDを引く必要がある。
- **今のトークン**：`verifyToken()` は id しか返さない。「今のトークン以外を消す」には、トークンの文字列そのものが要る。
- **中継の許可リスト**：server は3組（login・save_emotion・dashboard_data）、全体で8組。テストも「8つの組」。
- **テスト**：今は78個。PHP には自動のテストがない（確認はアプリと DB で行う）。

## 4. 設計

### 4.1 サーバー

**`tumugi_server/includes/login_guard.php`（新しく作る）**
- `login.php` から次を移し、`login.php` と `change_password.php` で共有する。`login.php` の動きは変えない。
  - 定数：`MAX_FAILED_ATTEMPTS = 5`、`LOCKOUT_WINDOW_MINUTES = 15`
  - `countRecentFailures(PDO $pdo, string $employeeCode): int`
  - `recordAttempt(PDO $pdo, string $employeeCode, bool $succeeded): void`

**`tumugi_server/includes/db.php`**
- `getBearerToken(): ?string` を足す。`Authorization: Bearer <token>` のトークン文字列を返し、なければ null。
- `verifyToken()` は、`getBearerToken()` を使うように直す（動きは変えない）。

**`tumugi_server/api/change_password.php`（書き直す）**

順に確かめ、どこかで止まったらその応答を返す。

| 順 | 確かめること | 止まったときの応答 |
|---|---|---|
| 1 | POST か | 405 |
| 2 | トークンが有効か（`verifyToken()`） | 401「認証が必要です」（アプリはログアウトする） |
| 3 | 在籍している社員か（`is_active = 1`）。同時に社員IDとハッシュを取る | 403「このアカウントは使えません」 |
| 4 | 直近15分の失敗が5回未満か | 429「試行回数が上限を超えました。15分ほど時間をおいてから再度お試しください」 |
| 5 | 今のパスワードが正しいか | 失敗を記録して 403「今のパスワードが正しくありません」 |
| 6 | 新しいパスワードが8文字以上か（`mb_strlen` で数える） | 400「新しいパスワードは8文字以上にしてください」 |
| 7 | 新しいパスワードが72バイト以下か（`strlen`） | 400「新しいパスワードが長すぎます（72バイトまで。全角なら24文字程度）」 |
| 8 | 今と同じでないか | 400「今と同じパスワードにはできません」 |

- 今のパスワードを先に確かめるのは、間違えた回数を必ず数えるため。
- すべて通ったら、1つのトランザクションで2つを行う。
  - `employees` の `password_hash` を `password_hash($new, PASSWORD_BCRYPT)` に変える。
  - `auth_tokens` から、この社員の、今のトークン以外を消す。
- 200 で `{"status":"ok","revoked":<消したトークンの数>}` を返す。

### 4.2 アプリ

**`net-policy.js`**
- server に `{ method: "POST", path: "/change_password.php" }` を足す（全体で9組）。
- テストを直す。「9つの組」にし、`GET /change_password.php` は拒否されることを足す。

**`js/password.js`（新しく作る。`TumugiPassword`）**
- ほかのモジュールと同じ形（IIFE で `module.exports` と `globalThis.TumugiPassword`）にする。
- `validateNewPassword({ current, next, confirm })` は `{ ok: true }` か `{ ok: false, message }` を返す。決まりは、上から順に次のとおり。

| 順 | 決まり | 出す文 |
|---|---|---|
| 1 | 今のパスワードが空 | 「今のパスワードを入れてください」 |
| 2 | 新しいパスワードが8文字未満（`Array.from` で数える） | 「新しいパスワードは8文字以上にしてください」 |
| 3 | 新しいパスワードが72バイトを超える（`TextEncoder` で数える） | 「新しいパスワードが長すぎます（72バイトまで。全角なら24文字程度）」 |
| 4 | 今と同じ | 「今と同じパスワードにはできません」 |
| 5 | 「もう一度」と一致しない | 「新しいパスワード（もう一度）が一致しません」 |

- テスト（`test/password.test.js`）
  - 5つの決まりのそれぞれ。
  - 通る場合。
  - 絵文字1つを1文字と数えること。
  - 全角24文字（72バイト）は通り、25文字は通らないこと。

**`memory-crypto.js`**
- `reencryptMemory(oldKey, record, newKey, newSaltValue)` を足す。古い鍵で復号し、新しい鍵とソルトで暗号化した新しいレコードを返す。古い鍵が違えば例外。
- テスト
  - 新しい鍵で読める。
  - 古い鍵では、新しいレコードを読めない。
  - 違う鍵を古い鍵として渡すと、例外になる。

**`main.js`**
- IPC `memory:rekey`（引数は新しいパスワード）
  - 展示モードでは、何もせずに true。
  - ログインしていない（`memorySession` がない）か、パスワードが空なら false。
  - 新しいソルトと鍵を作る。保存済みの記憶があれば `reencryptMemory` で付け替えて保存する。付け替えに失敗したら（壊れているなど）、その記憶は消す。
  - `memorySession` を新しい鍵とソルトにして、true を返す。
- IPC `app:isExhibit`：展示モードかどうか（true／false）を返す。

**`preload.js`**：`memoryRekey(newPassword)` と `isExhibitMode()` を足す。

**画面（`index.html`・`js/script.js`・`css/style.css`）**
- 「プライバシー設定」を「設定」に改める（ボタンとモーダルの見出し）。
- 「パスワードの変更」欄を足す。
  - 入力欄は3つ（今・新・新もう一度）。どれも `type="password"`。`autocomplete` は `current-password` と `new-password`。
  - 「変更する」ボタンと、結果を出す場所（`role="status"`）を置く。
  - 注意書き：「今のパスワードを5回間違えると、ログインも含めて15分ほど使えなくなります」。
- 「変更する」を押したときの流れ
  1. `validateNewPassword` で確かめる。だめなら理由を出す。
  2. ボタンを押せなくして、`POST /change_password.php` を送る（トークン付き）。
  3. 応答で分ける。
     - **成功**：`memoryRekey(新しいパスワード)` を呼び、「変更しました。ほかの PC でのログインは切れました」と出して、入力を空にする。`memoryRekey` が false なら、「パスワードは変更しました。記憶の付け替えに失敗したため、次のログインで記憶が消えることがあります」と出す。
     - **401**：今までと同じくログアウトする。
     - **400・403・429**：サーバーの `error` の文を出す。
     - **つながらない**：「サーバーに接続できませんでした」と出す。
  4. ボタンを元に戻す。
- 展示モード（`isExhibitMode()` が true）では、欄ごと隠す。
- `alert()`・`confirm()` は使わない（Electron で入力欄が効かなくなる不具合があるため）。
- 画面の読み込み順に `js/password.js` を足す（`prompt` のあと、`lipsync` の前）。

**`README.md`**：「デモアカウント」に、「ログインしたあと、『設定』からパスワードを変えられます（展示モードでは出ません）」と書く。

### 4.3 確認の手順（ユーザーが行う）
1. `npm test` がすべて通る（78個に、増えた分を足した数）。
2. 変えた PHP に、文法の誤りがない（`php -l`）。
3. E048 で次を確かめる。
   - 何か話して、つむぎに覚えさせる。
   - 今のパスワードを違うものにして変更 →「今のパスワードが正しくありません」が出て、ログアウトしない。
   - 「もう一度」を違うものにする →「一致しません」。7文字にする →「8文字以上」。
   - 正しく変更 →「変更しました…」。
   - ログアウトして、古いパスワードではログインできず、新しいパスワードでログインできる。
   - 覚えさせた記憶が残っている。
4. 別の PC の代わりに、E048 で何度かログインしてトークンを増やしてから変更する。DB で、E048 のトークンが1つになっている。
5. 今のパスワードを5回間違える → 429 の文が出る。ログイン画面でも止まる。このあと、DB の `login_attempts` から E048 の失敗を消して戻す。
6. 展示モード（`start-demo.bat`）では、「設定」にパスワードの欄が出ない。
7. 最後に、E048 のパスワードを、アプリの「設定」から元の値（`.env` の `DEMO_PASSWORD`）に戻す。

## 5. 範囲外
- 社員の登録、管理者によるリセット、退職者のログイン停止（`verifyToken` で `is_active` を見ること）。
- トークンの期限のずれ、ログアウトしてもトークンが残ること（トークンの問題として、別に直す）。
- パスワードの強さのチェック（よくあるパスワードを断るなど）。

## 6. リスクと対策
- **サーバーで変えたあと、記憶の付け替えに失敗する**：次のログインで記憶が読めず、消える。画面で知らせる（4.2）。
- **今のパスワードを5回間違えると、ログインも15分止まる**：意図どおり（乗っ取りを防ぐため）。欄の注意書きで知らせる。
- **ほかの PC でのログインが切れる**：意図どおり。成功のメッセージで知らせる。
