# サーバー（PHP の API）の自動テスト 設計書（2026-11-11）

## 1. 背景と目的

- 全コードのレビュー（2026-11-11）で、サーバーに自動テストがないことが分かった（一覧の C3）。
- 次のテーマは、権限と集計を変える直し（一覧の B1）。いちばん間違えてはいけない所を変えるので、その前に「今の動き」をテストで固定する。
- 目的：サーバーの API の今の動きを、コマンドで確かめられるようにする。直しで動きが壊れたら、すぐ分かるようにする。

## 2. 決定事項（2026-11-11 にユーザーと合意したもの）

- 言語の構成（Electron ＋ 素の JavaScript、PHP、MySQL）は変えない。
- テストは node:test で書く。API を HTTP で呼び、返ってきた状態コードと JSON を確かめる。新しいパッケージは入れない。
- テスト用の環境は、別の Compose ファイルで丸ごと別に立てる。デモの DB には触れない。
- API だけでは作れないデータは、テスト専用の PHP スクリプトを、テスト用のコンテナの中で呼んで用意する。
- 範囲は全部の API（11本）。
- サーバーのコード（`tumugi_server`）は変えない。

## 3. やらないこと

- サーバーのコードの直し。テストしにくい所が見つかっても、記録するだけにする。
- レビューの一覧で不具合とした動きのテスト（6章）。直すときに、直しと一緒に足す。
- アプリ（Electron）の画面のテスト。
- CI（一覧の C4）。あとで載せられる形にはしておく。

## 4. 設計

### 4.1 ファイルの置き場所

```
compose.test.yaml              テスト用の環境（リポジトリの直下）
tests/server/
  helpers.js                   共通の関数（API を呼ぶ、データを用意する、向き先を確かめる）
  *.test.js                    テスト本体（API ごとに1ファイル）
  fixtures/fixture.php         データを入れる・空に戻す・中身を読む（コンテナの中で動かす）
```

- `tumugi_server` の中には何も足さない。本番のサーバーに、テスト用のコードは入らない。

### 4.2 テスト用の環境（compose.test.yaml）

- プロジェクト名は `tumugi-test`。デモ（`tumugi`）とは、コンテナもネットワークもデータも分かれる。
- DB：`mysql:8.4`。データは保存しない（tmpfs）。立てるたびに、`tumugi_server/sql/schema.sql` からまっさらに作る。DB の名前は `tumugi_test`。
- サーバー：今の `docker/app` をそのまま使う。`127.0.0.1:8082` で受ける。`tumugi_server` を読み取り専用で載せる。
- `tests/server/fixtures` を、読み取り専用で `/var/www/tumugi-test-tools` に載せる。Apache が外に出すのは `/api` だけなので、ここはウェブからは呼べない。
- DB の名前・ユーザー・パスワードは、テスト専用の値を `compose.test.yaml` に直接書く（`.env` は使わない）。この DB は 127.0.0.1 にも出さず、中身はテストのデータだけなので、秘密ではない。
- デモの環境と同時に立てておける（プロジェクト名・ポート・DB が違う）。
- 先頭に `name: tumugi-test` を書く（書かないと、フォルダの名前からデモと同じプロジェクト名になる）。
- MySQL には、デモと同じく `--default-time-zone=+09:00` と `TZ: Asia/Tokyo` を付ける。
- `--wait` で待てるように、DB に healthcheck を付ける。
- パスワードの値は、引用符で囲まずに書く（公開版を作るときの確認が、引用符つきの `…PASSWORD: "値"` の形を見つけて止まるため）。

### 4.3 データの用意（fixture.php）

- テストから `docker compose -f compose.test.yaml exec -T app php /var/www/tumugi-test-tools/fixture.php` で呼ぶ。命令は標準入力の JSON で渡し、結果は JSON で受け取る。
- できること：
  - 全部のテーブルを空に戻す。
  - 社員を入れる（社員ID・部署・新卒・管理者・在籍・仮のパスワードかどうか・パスワード）。パスワードのハッシュは、サーバーと同じ `password_hash` で作る。
  - 感情ログを入れる（社員・感情・スコア・危機・ハラスメント・何日前か）。
  - ログインの試行を入れる（社員ID・成功か失敗か・何分前か）。
  - トークンの期限を過去にする。
  - 確かめのために読む：操作の記録（`admin_audit_logs`）、テーブルごとの行の数、社員1人の行、社員1人の感情ログの行、社員ごとのトークンの数とログインの試行の数。
- 読む機能が要る理由：退職は在籍の印、リセットは仮のパスワードの印でも API が 401 になるので、API を呼ぶだけでは「トークンを消す処理」が壊れても気づけない。DB の行で確かめる。
- 命令は、いくつかまとめて1回で渡せるようにする（コンテナの中で動かすのは1回に0.5〜1秒かかるため）。
- 空に戻すときは、外部キーの確認を止めてから5つのテーブルを空にする。
- 過去の時刻は、PHP の時計ではなく SQL の `NOW() - INTERVAL …` で入れる（サーバーが比べるのも MySQL の時計のため）。
- パスワードのハッシュ（bcrypt）は、同じパスワードなら使い回してよい。
- DB へは、サーバーの `includes/db.php` を読み込んでつなぐ（同じ環境変数を使う）。

### 4.4 取り違えを防ぐ

- `helpers.js` は、向き先が `http://127.0.0.1:8082` でなければ、テストを始めない。
- `fixture.php` は、DB の名前が `tumugi_test` でなければ、何もせずに終わる。
- どちらか片方を間違えても、デモの DB は変わらない。

### 4.5 テストの書き方

- テストごとに、最初に DB を空に戻し、要るデータだけを入れる。前のテストの残りに頼らない。
- テストは1つずつ順に動かす（ファイルの中も、ファイルどうしも）。同じ DB を使うため。
- パスワードは、動かすたびに乱数で作る。ファイルに書かない（公開版を作るときの確認が、そのまま書かれたパスワードを見つけて止まるため）。
- 時間のかかる条件は、待たずにデータで作る（16分前の失敗、8日前の記録、期限の切れたトークン）。
- テストは CommonJS で書き、リポジトリの直下から動かす。
- 社員IDは `E001` のように大文字にそろえる（DB は大文字・小文字を区別せずに並べる）。
- 「違うパスワード」やトークンも、文字列をそのまま書かず、乱数で作った値を変数で渡す（公開版を作るときの確認に当たらないように）。
- API は、入力を上から順に確かめる。ある 400 や 404 を確かめるときは、ほかの項目は正しい値で送る（例：修正の「いない社員は 404」は、名前・部署・新卒・管理者も付けて送る。パスワード変更の 400 は、今のパスワードを正しく送る）。
- 401・403 のテストは、正しい HTTP メソッドで送る（メソッドの確認のほうが先のため）。
- 確かめるのは、状態コードと JSON の中身。エラーの文は、種類を見分けるのに要るときだけ確かめる（文を直すたびにテストが壊れないように）。

### 4.6 動かし方（ユーザーが実行する）

1. テスト用の環境を立てる：`docker compose -f compose.test.yaml up -d --build --wait`
2. テストを動かす：`node --test --test-concurrency=1 "tests/server/*.test.js"`
3. 片づける：`docker compose -f compose.test.yaml down`

- README の「テスト」に、この手順を足す。
- 環境が立っていないときは、最初に「テスト用の環境が立っていません」と分かる文を出して止まる。

## 5. テストの一覧（約80個）

今の動き（HEAD 3d2f17e）を、そのまま確かめる。

### 5.1 共通（5）
- 管理者用の API（7本）は、トークンがないと 401。
- 管理者用の API（7本）は、管理者でない社員だと 403。
- POST の API に GET で来ると 405（一覧の API は、POST で来ると 405。ダッシュボードはメソッドを見ないので、対象外）。
- 管理者でも、退職にした・仮のパスワードのままなら、管理者用の API は 401。
- 管理者用の API の応答に、パスワードのハッシュは入らない。

### 5.2 ログイン `login.php`（11）
- 正しい社員IDとパスワードで 200。`token`・`employee_id`・`department`・`is_admin`・`must_change_password`・`expires_in`（86400）が返る。
- パスワードが違うと 401。
- いない社員IDでも 401。エラーの文は、パスワードが違うときと同じ。
- 社員IDかパスワードが空だと 400。
- 退職にした社員は 401。
- 仮のパスワードの社員は、ログインでき、`must_change_password` が true。
- 失敗が5回あると、6回目は正しいパスワードでも 429。
- 16分前の失敗は数えない（5回あってもログインできる）。
- 成功した回は、失敗の数に入らない。
- 社員IDは、大文字・小文字が違っても、前後に空白があってもログインできる。
- ログインすると、期限の切れたトークンが（ほかの社員の分も）消える。

### 5.3 ログアウト `logout.php`（3）
- トークンがないと 400。
- ログアウトしたトークンは、もう使えない（`save_emotion.php` が 401）。
- 知らないトークンでも 200（何も消えない）。

### 5.4 感情ログ `save_emotion.php`（9）
- トークンがないと 401。期限の切れたトークンも 401。
- 仮のパスワードのままの社員は 401。
- 退職にした社員のトークンは 401。
- 感情ごとのスコア：happy 0・normal 10・tired 50・angry 50・anxious 60・sad 70（`recorded_score`）。
- `is_crisis` が true なら、感情が何でもスコアは 100。
- 知らない `emotion` は 400。前の分類の `surprised`・`troubled` も 400。
- 知らない `harassment_type` は 400。
- 記録は、その社員の行として1行増える。保存された感情・スコア・危機・ハラスメントを、DB の行で確かめる。

### 5.5 パスワード変更 `change_password.php`（9）
- トークンがないと 401。
- 変えたあとは、新しいパスワードでログインでき、古いパスワードではできない。
- 今のパスワードが違うと 403。
- 新しいパスワードが8文字未満だと 400（全角も1文字と数える）。
- 新しいパスワードが72バイトを超えると 400。
- 今と同じパスワードは 400。
- 仮のパスワードの社員が変えると、`save_emotion.php` が通るようになる。
- ほかのトークンは消え、今のトークンは残る（`revoked` の数）。
- 今のパスワードを5回間違えると、6回目は 429。

### 5.6 ダッシュボード `dashboard_data.php`（14）
- 記録のある在籍社員が9名の部署は出ない。出せる部署が1つもないときは `note` が入る。
- 10名の部署は出る。`min_dept_size` は 10。
- 平均は「社員ごとの平均」の平均で、小数1桁（記録の多い人に引っぱられない）。`avg_score` は文字列（例：`"35.0"`）で返るので、数に直して比べる。
- `log_count` は、その部署の記録の数。
- 8日前の記録は入らない。6日前の記録は入る。
- 退職にした社員の記録は入らない（人数にも平均にも）。
- 部署の危機：0人なら `none`。
- 部署の危機：1〜9人なら `flag_only`（件数は返らない）。
- 部署の危機：10人以上なら `count`（件数が返る）。
- 新卒：記録のある新卒が9名なら `new_grad` は null で、`new_grad_note` が入る。
- 新卒：10名なら、部署をまたいだ平均・記録の数・危機が返る。
- ハラスメント：`received` と `said` を別々に数える（受けた9人＋言った1人は、どちらも `flag_only`）。
- ハラスメント：同じ種類が10人以上なら `count`。0人なら `none`。
- ハラスメント：退職にした社員の記録は入らない。

### 5.7 社員の一覧 `admin_employees.php`（2）
- 全員が社員IDの順に返る（退職者も、仮のパスワードの印も）。`self_code` は呼んだ管理者。
- `departments` は、在籍している社員の部署だけ。

### 5.8 社員の登録 `admin_employee_create.php`（8）
- 成功で、12文字の `temp_password` が返る。その社員は仮のパスワードの状態で、ログインできる。
- 同じ社員IDは 409。大文字・小文字だけが違う社員IDも 409。
- 社員IDの形が違うと 400（21文字、記号、空）。
- 社員ID「CLI」は、大文字でも小文字でも 400。
- 名前・部署が空、または51文字だと 400。50文字は通る。
- `is_new_grad`・`is_admin` が true/false でないと 400。
- 操作の記録に `create` が1行増える。

### 5.9 社員の修正 `admin_employee_update.php`（6）
- 部署と新卒の印を変えられる。操作の記録の `detail` は、変えた項目の名前（並びは display_name・department・is_new_grad・is_admin の順）。
- 何も変わらないときは 200 で、操作の記録は増えない。
- いない社員は 404。
- 自分を管理者から外すのは 400。
- ほかの管理者を、管理者から外せる（管理者が2人いるとき）。
- `is_new_grad`・`is_admin` が true/false でないと 400。

### 5.10 退職・在籍 `admin_employee_status.php`（6）
- 退職にすると、その社員のトークンは使えなくなり、ログインもできない。トークンの行が消えたことを DB で確かめる。操作の記録は `deactivate`。
- 在籍に戻すと、ログインできる。操作の記録は `reactivate`。
- 自分を退職にするのは 400。
- すでに退職の社員を退職にしても 200 で、操作の記録は増えない（在籍も同じ）。
- `is_active` が true/false でないと 400。
- いない社員は 404。

### 5.11 リセット `admin_employee_reset.php`（4）
- `temp_password` が返る。古いパスワードではログインできず、仮のパスワードでできる。`must_change_password` は true。
- その社員のトークンは使えなくなり、ログインの失敗の数は消える（ロック中でもログインできるようになる）。トークンの行と失敗の行が消え、成功の行は残ることを DB で確かめる。
- 自分は 400。
- いない社員は 404。

### 5.12 削除 `admin_employee_delete.php`（5）
- 在籍中の社員は 400。
- 確かめの社員IDが違うと 400（大文字・小文字も区別する）。
- 成功で、一覧から消える。その社員の感情ログとログインの試行も消える。操作の記録は `delete`。
- 自分は 400。
- いない社員は 404。

## 6. 今回テストに入れない動き

- レビューの一覧で不具合とした動き。直すときに、正しい動きのテストを足す。
  - 社員IDが長い・型が違うと 500 になる（A5）。
  - 4回間違えたあとに成功しても、失敗の数が消えない（A8）。
  - CORS のヘッダーと OPTIONS の応答（B2）。
  - `save_emotion.php` に `emotion` を付けずに送ると normal として記録される（A5 の一部）。
- 「在籍している管理者がいなくなる操作は断る」（`admin_employee_update.php`・`admin_employee_status.php`）。
  - 呼んだ管理者が在籍していて、自分自身への操作は先に断られるので、ふつうの呼び方ではこの分岐に入らない（2つの操作が同時に来たときの守り）。テストでは作れないので、入れない。
- DB につながらないときの 500。
- `tools/admin_setup.php` と `tools/seed_demo.php`（コマンドの道具）。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| テストがデモの DB を変える | 環境を丸ごと分ける。向き先と DB の名前を、2か所で確かめる（4.4） |
| テストが遅い（bcrypt、HTTP、コンテナの中のスクリプト） | ログインが要らないデータは fixture で直接入れる。fixture への命令はまとめて1回で渡す。全体で3〜5分を目安にする |
| 日付の境目でたまに落ちる | 境目ちょうど（7日・15分）は使わず、余裕のある値（6日と8日、16分）で確かめる |
| テストどうしが影響し合う | テストごとに DB を空に戻す。1つずつ順に動かす |
| エラーの文を直すとテストが壊れる | 文は、種類の見分けに要るときだけ確かめる |
| 公開版の確認で止まる | パスワードをファイルに書かない（乱数で作る） |

## 8. 実装する人に任せること

- `helpers.js` の関数の名前と分け方。
- `fixture.php` の命令の JSON の形。
- テストのファイルの分け方（API ごとを基本に、近いものはまとめてよい）。
- 5章の1行を、いくつのテストに分けるか（個数は目安）。
