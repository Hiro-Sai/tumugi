## 1. 背景と目的

### 背景
- 実運用の必須条件は「事務用 PC（GPU なし、メモリ 8〜16GB）でも動くこと」。
- 今のアプリを CPU だけで動かすと、発言してから文字が出るまで約27秒かかる。全文がそろうまでは約30秒（2026-10-27 の測定。このノート PC で `num_gpu 0`・4スレッドにして、事務用 PC をまねた）。
- 遅い原因は、生成ではなく入力の読み込み（プロンプトの処理）。
  - Gemma 4 は SWA という仕組みを使っている。そのため Ollama のキャッシュは、前の入力の終わり（区切りの印がある場所）からしか続きを使えない。
  - 今のアプリは、毎回入力の途中を変えている。そのため、判定と返事のどちらも、毎回ほぼ最初から読み直している。
    - 判定の入力は、直前の2往復をまとめた文を作り直す。
    - 返事の入力は、履歴から今回のノートを外す。記憶と要約が変わると、システムプロンプトも変わる。

### 目的
- CPU だけの PC でも、発言してから10秒以内に文字が出はじめ、残りが少しずつ続くようにする。
- 安全判定の精度と、返事の質は落とさない。

### 成功基準
- **ふつうの回の待ち時間**：このノート PC で CPU だけにして（4.7 の確かめ用の起動オプション）、2回目以降の発言で、line の最初の文字が出るまで10秒以内。測定の案 b では5.2〜8.3秒だった。
- **1回目の待ち時間**：ログインしてから15秒後に発言したとき、10秒以内。
- **判定の精度**：測定に使った68文（`.superpowers/spike-llm/cpu-first.mjs` の57文と、「話題が変わったあと」の11文）で、次のとおりになる。
  - 危機の見逃しが、今のアプリより増えない。今のアプリの見逃しは、hc2（流れなし）と x5。
  - 誤検知が、今のアプリより増えない。
- **返事の質**：line の長さと受け止めの厚さが、今のアプリと同じくらいになる。測定では、line の平均が今のアプリ31.8字、案 AQ 31.0字だった。
- **声と表情**：今と同じく、全文がそろってから読み、全文がそろってから表情を変える。
- **GPU の PC**：今より遅くならない。
- **ローカル完結**：新しい接続先を足さない。
- `npm test` がすべて通る。

## 2. 決定事項

ユーザーと合意したもの（2026-10-27）。

1. 目標は「発言してから10秒以内に文字が出はじめ、残りは少しずつ続く」。
2. 声は、全文がそろってから読む（今と同じ）。1文ずつ読みはじめる形は作らない。
3. 立ち絵の表情は、全文がそろってから変える（今と同じ）。
4. 文字の出し方
   - line は、届いたところから吹き出しに少しずつ出す。
   - 全文がそろったら、line を読み、そのあと share と question を、今と同じく吹き出しに出しながら読む。
5. 安全判定は、返事と別の呼び出しのまま残す。危機の見逃しを増やさない。返事の質を落とさない。すべてローカルで動かす。
6. 測るのはこのノート PC だけにする。`num_gpu 0`・4スレッドで、事務用 PC をまねる。
7. 先に測ってから設計書を書く。測定は4回行った（3章）。
8. 要約による履歴の切り替えは、めったに起こさない（目安は40往復）。起きたときに社員がすぐ発言すると、1回だけ30秒ほど待つことになるが、それでよい。
9. 会話の途中で、記憶の画面から記憶を直したり消したりしたときは、今と同じく、すぐ今の会話に反映する。そのあとの発言が1回だけ遅くなることがあるが、それでよい（4.4 の6）。
10. 判定に渡す会話は、判定の指示と、直近の3件（ログイン時のあいさつも1件、1往復も1件と数える）と、今回の発言にする。返事の履歴は今のまま。会話の全体を渡すと、長い会話のあとで判定が甘くなり、危機の見逃しが増えたため（3章「長い会話のあとの判定」。2026-11-02 に合意）。

## 4. 設計

### 4.1 全体の決まり（キャッシュを効かせるため）

- **継ぎ足すだけ**：判定と返事のそれぞれで、送る入力は、前に読ませた入力の後ろに足したものにする。途中は変えない。
  - 途中を変えてよいのは、次の3つだけ。
    - 直前の発言からノートを外すこと（4.3）
    - 要約などで履歴を作り直すこと（4.4）
    - 判定に渡す直近3件が、1件ずつ後ろへずれること（4.2）。そのぶん、返事のあとに判定の整えを送る（4.4 の1）
- **呼び出しの設定をそろえる**：判定・返事・記憶・要約・先読み・整えのすべてで、モデルと、読み込みに関わる設定（`num_ctx` など）を同じにする。値が違うと、モデルを読み込み直す。
- **止めない**：裏の呼び出しは、途中で止めない（止めても早くならず、キャッシュも壊れる。3章）。Ollama の順番待ちに任せる。
- **時間だけを記録する**：確かめのために、各呼び出しの入力の語数・処理時間・生成時間を `console` に出す。発言や返事の中身は出さない。

### 4.2 安全判定（c2）

- 判定専用の指示は、測定の c2 と同じ文にする。`js/safety.js` の `CLASSIFY_INSTRUCTION` を置き換える。
  - c2 は、今の指示の3行目から後ろ（`"crisis"` と `"harassment"` の決め方・`"reason"`・出力例）を、そのまま使う。
  - その前の行で、次のことを書く。
    - 会話の読み方（user が社員、「つむぎ：」で始まる assistant がつむぎの返事）
    - 判定するのは最後の user の発言だけであること
    - 前のやり取りは意味を読み取るためだけに使い、話題が変わったら入れないこと
  - 文の全体は次のとおり（測定の `cpu-first.mjs` の `CHAT_JUDGE_INSTRUCTION_2` と同じ）。4行目のあとに空の行を1つ置き、そのあとに今の指示の3行目から最後までを、1文字も変えずに続ける。

```
あなたは、相談アプリ「つむぎ」の会話を読んで、安全判定だけを行う係です。ユーザーへの返事は書きません。
これから渡す会話で、user はアプリを使っている社員、assistant（「つむぎ：」で始まる文）は相談アプリ「つむぎ」の返事です（あなたの発言ではありません）。
会話の最後の user の発言が「今回の発言」です。判定するのは、今回の発言だけです。
それより前のやり取りは、今回の発言の意味を読み取るために使うこと。前のやり取りに危機やハラスメントの話があっても、今回の発言がその話の続きでなければ、今回の判定には入れない。

"crisis": 今回の発言（とそこまでの流れ）に、……（今の CLASSIFY_INSTRUCTION の3行目から最後まで）
```
- **判定の入力**：[判定の指示（system）, 判定用の履歴…, 今回の発言（user）]
  - 今回の発言は、社員の文だけ。ノートは付けない。
- **判定用の履歴**：返事の履歴と同じ並びにする。
  - user：社員の発言（ノートなし）
  - assistant：「つむぎ：」＋つむぎの返事の文（line・share・question を全角の空白でつないだもの。今の `conversationHistory` と同じ）
  - ログイン時のあいさつも、assistant として最初に入れる（直近3件のうちに入っているあいだ）。
  - 判定に渡すのは、直近の3件だけ（あいさつも1件、1往復も1件と数える）。3件を超えたら、古いほうから外れる。会話の全体を渡すと、長い会話のあとで危機の見逃しが増えたため（3章「長い会話のあとの判定」）。
- **キーワードや判定で危機になった回**：社員の発言と相談先の案内（`CRISIS_SUPPORT_LINES` をつないだもの）を、判定用の履歴にも返事の履歴にも足す。今の `showCrisisSupportMessages` と同じ扱い。
- **判定に失敗した回**：履歴には、ほかの回と同じように足す。履歴の並びを、返事の履歴とずらさないため。
- `buildClassifyMessage` と `CLASSIFY_HISTORY_TURNS` は使わなくなるので消し、テストも新しい形に書き換える。

### 4.3 返事の履歴（AQ）

- **返事の入力**：[システムプロンプト（system）, 返事の履歴…, 今回の発言＋ノート（user）]
- **システムプロンプト**：今と同じく、キャラクターの指示に、記憶と要約を足したもの。
  - 中身は、ログインしたときと、履歴を作り直したとき（4.4）にだけ決める。
  - 会話の途中で記憶が増えても、システムプロンプトは変えない。
- **今回の発言の後ろに付けるもの**：今と同じく `TumugiPrompt.withDynamicNote` で付ける。
  - 感情の流れの注意と、言い方の重複回避（今の `buildDynamicNote`）
  - 前の回から新しく覚えたこと。見出しは「【このユーザーについて新しく分かったこと】」。測定の `factsNote` と同じ形。
- **返事の履歴に残すもの**
  - user：社員の発言。新しく覚えたことがあった回だけ、その見出しと中身も残す。感情の流れの注意と、言い方の重複回避は残さない。
  - assistant：つむぎの返事の文（JSON ではなく、line・share・question を全角の空白でつないだもの）
- **新しく覚えたこと**：記憶の抽出（今と同じく3往復に1回、裏で行う）で新しく分かったことは、次の発言の後ろに1回だけ付ける。記憶の保存は、今と同じ。
- **「はじめまして」で名前などを入れたとき**：あいさつより前の話なので、ログイン後の先読み（4.4）の前に、システムプロンプトへ入れる。

### 4.4 裏の処理

どれも返事を出し終えてから送り、終わるのを待たない。順番は Ollama の順番待ちに任せる。

1. **整え**（毎回、返事のあとすぐ）
   - 危機の案内を出した回のあとにも送る。Ollama につながらなかった回のあとは送らない（実装で決めた）。
   - 入力は [システムプロンプト, 今回の分まで足した返事の履歴（最後は assistant）]。続きを書かせる形で、1語だけ書かせる。
   - 次の返事の入力が、直前の発言からノートを外した形でもキャッシュを使えるようにするため（3章）。
   - 測定では、1回0.6〜1.7秒だった。
   - 返事の整えのあとに、**判定の整え**も送る。入力は [判定の指示, 新しい直近3件（最後は assistant）]。判定に渡す3件がずれても、次の判定でキャッシュが効くようにするため（4.2）。整えと同じく、危機の案内を出した回のあとにも送り、つながらなかった回のあとは送らない。
2. **記憶の抽出**：今と同じ（3往復に1回）。
3. **ログイン画面での先読み**
   - ログイン画面を開いたら、モデルを読み込み、判定の指示だけを読ませておく。社員がログインの情報を打っているあいだに済ませる。
   - 判定の指示は社員によらないので、ログインの前に読ませておける。
   - 測定では、モデルの読み込み6.5秒＋判定7.6秒だった。
   - 測ったのは、あいさつまでを入れた形だけ。判定の指示だけを読ませた形で、ログインのあとにキャッシュが効くかは、まだ確かめていない。効かなくても、モデルの読み込みの分は早くなる。4.9 の3で確かめる。
   - 結果：ログイン後の1回目は約8秒で、10秒以内に入った（3章「実装したあとに確かめたこと」）。目標に入ったので、キャッシュが効いたかどうかは記録していない。
4. **ログイン後の先読み**
   - あいさつを出したら、まず判定の [判定の指示, 「つむぎ：」＋あいさつ] を、続きを書かせる形で読ませる。そのあと、返事の [システムプロンプト, あいさつ] も同じように読ませる。
     - 判定を先にするのは、社員の1回目の発言で最初に送るのが判定で、判定の先読みは短く済むため。
   - 返事のシステムプロンプトは記憶で変わるので、ログインのあとにしかできない。測定では16.5秒だった。
   - チャット画面を読み込み直したとき（あいさつを出さないとき）は、履歴がないまま、システムプロンプトだけを読ませる。
5. **要約と、履歴の作り直し**
   - **きっかけ**：会話の流れが80件（40往復）を超えたとき、または返事の入力が6000語（トークン）を超えたとき。語数は、返事の応答の `prompt_eval_count` で分かる。今は20件。
   - **要約**：今と同じ文で裏で作る。要約の入力は判定や返事と前半が違うので、今の履歴のキャッシュは残る。
   - **作り直し**：要約ができたら、すぐに次のように作り直す。
     - 返事のシステムプロンプトに、今の記憶と要約を入れる。
     - 判定用の履歴と返事の履歴の、どちらからも、要約に使った分を消す。残るのは、要約を頼んだときの最後の10件（今の `SUMMARY_KEEP` と同じ）と、そのあとに足した分。
     - 残した発言から、「新しく分かったこと」を消す。記憶はシステムプロンプトに入ったため。
     - 社員の発言を処理している途中（判定を送ってから、声を読み終えるまで）に要約が届いたときは、その回の分を履歴に足し終えてから作り直す。回の途中で履歴を入れ替えると、その回の分がどちらの履歴に入るか分からなくなるため。
   - **作り直しのあと**：判定、返事の順に、続きを書かせる形で先読みする。
     - 判定に渡す直近3件にした（2章の10）あとは、返事だけを先読みする。要約しても最後の10件は残るので、判定に渡す3件は作り直しで変わらないため。
     - 社員がそのあいだに発言したら、Ollama の順番待ちで、先読みが終わるまで待つ。測定では、要約に11〜13秒、判定の先読みに5〜7秒、返事の先読みに12〜14秒かかった。
     - 待ったあとは、新しい履歴のキャッシュが効く。
   - 作り直しの途中で、古い履歴に戻すことはしない。
6. **記憶の画面で、記憶を直した・消した・全部消したとき**
   - すぐに作り直して、返事の先読みをする。
     - 返事のシステムプロンプトに、直したあとの記憶と、今の要約を入れる。
     - 履歴は短くしない（要約は作らない）。
     - 残した発言から、「新しく分かったこと」を消す。
     - 判定用の履歴は変わらないので、判定の先読みは要らない。
   - 今のアプリと同じく、消した記憶を、つむぎが次の返事から使わないようにするため。
     - ただし、その会話の中で社員が話した内容は、今と同じく履歴に残る。
   - 次の発言は、1回だけ遅くなることがある。CPU だけの PC では、20往復なら30秒ほど。
   - 社員の発言を処理している途中に記憶を直したときは、5と同じく、その回が終わってから作り直す。

### 4.5 少しずつ表示

- **中継**：Ollama の `/api/chat` を `stream: true` で受け取る中継を、新しく足す。今の `net:ollamaRequest` と同じ決まりで守る。
  - 許可する接続先は同じ。
  - PC の中で動くモデルにだけ送る。
  - 展示モードの `keep_alive` も同じ。
  - 届いた文字のかけらを、頼んだ画面にだけ渡す。終わったら、今の中継と同じ形の結果を返す。
    - 成功：`{ ok: true, data }`。`data` には、つないだ全文と、最後に届いた `prompt_eval_count` などの数を入れる。
    - 失敗：`{ ok: false, reason }`
- **画面**
  - 返事の JSON は、user_emotion → emotion → line → share → question の順に生成される。届いた文字から line の部分を取り出し、吹き出しに少しずつ出す。
  - JSON の途中を読む部分は、画面に依存しない関数にして、テストする。エスケープ（`\"`・`\n`・`\uXXXX`）が途中で切れていても、こわれた文字を出さないこと。
  - 全文がそろったら、`parseReply` で確かめてから、次の順に進める。ここからは今の `showTwoPartResponse` と同じ。
    1. 表情を変える。
    2. 感情ログを送る。
    3. line を読む。
    4. share と question を、吹き出しに出しながら読む。
  - 少しずつ出した line と、確かめたあとの line が違うときは、確かめたあとの line に置き換える。
- **壊れた返事**：途中まで出した吹き出しを消して、1回だけ作り直す。作り直しも少しずつ出す。それでもだめなら、今と同じく代わりの返事にする。
- **Ollama につながらないとき**：今と同じ案内を出す。履歴は、判定と返事のどちらも、発言と代わりの返事の組で足す。

### 4.6 そのほか

- 判定の呼び出しは、今と同じく少しずつではなく、一度に受け取る（数十語で終わるため）。
- 記憶の抽出の文、要約の文、`REPLY_SCHEMA`、`CLASSIFY_SCHEMA` は変えない。

### 4.7 確かめ用の起動オプション

- `--cpu-only` を付けて起動すると、main.js が Ollama へのすべての POST に `num_gpu: 0`・`num_thread: 4` を足す。このノート PC で、事務用 PC をまねて確かめるため。
- 付けないときは、今と同じ（GPU があれば使う）。
- 起動のしかたは README に書く。

### 4.8 テスト

画面に依存しない部分を分けて、`node --test` で確かめる。

- **会話の履歴を扱う部分**（判定用と返事用の両方）
  - 送る入力が、前に読ませた入力（整えの入力を含む）の後ろに足しただけになっていること
  - ノートは今回の発言にだけ付き、履歴には「新しく分かったこと」だけが残ること
  - 判定用の assistant に「つむぎ：」が付くこと
  - 判定に渡すのは直近の3件だけで、あいさつも1件と数えること。作り直しても、その3件が変わらないこと
  - 危機の回が、両方の履歴に足されること
  - 作り直しで、最後の10件が残り、「新しく分かったこと」が消え、システムプロンプトが変わること
  - 要約のきっかけ（80件、6000語）
- **JSON の途中から line を取り出す部分**：途中で切れた文、エスケープ、line がまだ来ていないとき、line が終わったあと
- **少しずつ受け取る中継の、届いたかけらを行に分ける部分**：1行が2つのかけらに分かれて届いたとき、最後の行など
- **判定の指示**：c2 の文になっていること。今の3行目から後ろの決め方が、そのまま入っていること

### 4.9 確認の手順（ユーザーが行う）

1. `npm test` がすべて通る。
2. 判定の精度を測り直す。68文に、案 b でゆれた2文（5回目・13回目の発言を、その前の流れごと）を足して測る。
   - 測るスクリプトは、計画のときに用意する。アプリの `js/safety.js` を読んで測る。
   - 成功基準と同じく、見逃しと誤検知が今より増えないこと。
3. `--cpu-only` を付けてアプリを起動し、20往復ほど話す。
   - ログイン画面で少し待ってから、ログインする。あいさつのあと15秒ほどで、1回目の発言をする。
   - DevTools の `console` で、毎回の待ち時間と入力の処理時間を見る。
   - ふつうの回は10秒以内に文字が出はじめること。
   - line が少しずつ出て、全文がそろってから声と表情が変わること。
4. 記憶の画面で1つ消してから話し、つむぎがその記憶を使わないことを確かめる。
5. GPU のまま（`--cpu-only` なし）で数往復話し、今より遅くないことを確かめる。
6. 40往復を超えるまで話して、要約の切り替えを1回起こす。
   - 切り替えのあとも返事の質が落ちないことを見る。
   - CPU だけで続けると時間がかかるので、GPU で測る使い捨てのスクリプトでもよい（計画のときに決める）。

## 5. 範囲外

- E2B などの小さいモデルへの切り替え
- 1文ずつ声にすること
- メモリ 8GB の PC での確認。Ollama のキャッシュがメモリを使う量（3章、上限8GB）も、そのときに見る。
- 裏の呼び出しを途中で止めること（3章のとおり、効かない）
- Ollama の自動更新を止めること（前からの課題）
- 管理者のダッシュボード
- ハラスメントの判定の見直し（3章「実装したあとに確かめたこと」）。何もない仕事の愚痴の文を増やし、同じ文を何回かずつ測ってから直す。
- line が発言をくり返すだけになりやすいこと（前のアプリから）
- 遠回しな言い方の危機（「保険金が出れば家族も助かる」など）を拾うこと（3章「長い会話のあとの判定」）。今のモデルでは、同じ文でも、前の会話が少し変わるだけで答えが変わる。

## 6. リスクと対策

- **Ollama の中の動きに頼っている**
  - 速さは、Ollama 0.40.11 のキャッシュと区切りの印の動き（3章）に頼っている。版が変わると、速さが戻るおそれがある。正しさは変わらない。0.40.13（10月30日の自動更新）でも、アプリの待ち時間と prompt_eval_count の数え方は同じだった（2026-11-02）。
  - 要約の語数のきっかけ（6000語）は、Ollama 0.40.11 の prompt_eval_count がキャッシュの分も含むことに頼っている。版が変わって新しく処理した分だけになると、件数のきっかけだけが残る。版を上げたら、console の返事の入力の語数が回ごとに増えていくことを確かめる。
  - 対策：時間を `console` に出す（4.1）。版を上げたら、4.9 の3で測り直す。
- **前半が少しでもずれると、黙って遅くなる**
  - 送る入力の途中が1文字でも変わると、エラーにはならず、遅くなるだけ。
  - 対策：継ぎ足すだけになっていることを、テストで確かめる（4.8）。入力の処理時間も `console` に出す。
- **40往復までの質と速さは、測っていない**
  - 測ったのは20往復まで。
  - 対策：4.9 の6で確かめる。悪ければ、きっかけの件数を下げる。
  - 結果：返事の質は45往復で確かめ、落ちていなかった（3章「実装したあとに確かめたこと」）。きっかけの件数は80件のまま。
  - 結果：判定は、会話の全体を渡すと、20往復のあとから危機の見逃しが増えた。判定に渡す会話を直近3件にした（3章「長い会話のあとの判定」、2章の10）。
- **判定に渡す会話の長さ**
  - 3件にしたのは、記録した1つの会話の2か所（20回目・39回目まで）で測った結果から。見分けにくい文（x4・hc2）は、前の話が少し増えるだけで答えが変わる。
  - 対策：作ったあと、同じ会話の別の場所（10回目・30回目まで）でも測る。足りなければ2件にする（定数1つ）。
  - 結果：30回目までで hc2 を見逃した。会話を渡さなくても見逃すことのある文なので、3件のままにした（3章「長い会話のあとの判定」）。
  - 毎回、返事のあとに判定の整えが1つ増える（CPU で3〜4秒、裏で）。`--cpu-only` で、ふつうの回の待ち時間が10秒以内のままかを確かめる。
  - 結果：アプリでは話を続けられたが、秒数は見ていない。8GB の PC での確認（5章）のときに、あわせて測る。
- **判定のゆれ**
  - 案 b の20往復で、ハラスメントの誤検知が2回あった。
  - 対策：4.9 の2で、その文を足して測る。
  - 結果：ゆれではなかった。指示は変えず、後のテーマにした（3章「実装したあとに確かめたこと」）。
- **1回目の待ち時間**
  - ログインしてすぐ（数秒で）発言すると、返事の先読みが終わっていないので、10秒を超える。
  - 測定では、ログインの前の先読みがない状態で、15秒後の発言が20.0秒だった。
- **メモリ**
  - Ollama が、キャッシュとして読ませた入力を何件も持つ。
  - 対策：8GB の PC での確認（範囲外）のときに見る。

## 7. 作り手に任せること・Claude の判断

### Claude の判断（設計書の確認で、ユーザーに見てもらう）
1. 判定は c2、返事の履歴は AQ にする（3章の結果から）。
2. ログイン画面のあいだに、モデルの読み込みと判定の指示の先読みを済ませる（4.4 の3）。
3. ログイン後と作り直しのあとの先読みは、判定、返事の順にする（4.4 の4）。
4. 要約のきっかけは80件（40往復）か6000語。残すのは今と同じ10件（4.4 の5）。
5. 発言の処理中に要約が届いたら、その回が終わってから作り直す（4.4 の5）。
6. 壊れた返事は、途中まで出した吹き出しを消して1回だけ作り直す（4.5）。
7. 裏の呼び出しは止めない（4.1）。
8. 確かめ用の起動オプション `--cpu-only` を足す（4.7）。
9. 各呼び出しの語数と時間を `console` に出す（中身は出さない。4.1）。
10. 判定の整えは、返事の整えのあとに送る。作り直しのあとは、判定の先読みをしない（4.4 の1・5。2026-11-02）。

### 作り手に任せること
- 会話の履歴を扱う部分の置き場所と名前。たとえば `js/conversation.js` を新しく作る。今の `safety.js`・`prompt.js` と同じく、画面とテストの両方から読める形にする。
- 少しずつ受け取る中継の IPC の形。たとえば、頼んだ画面にだけ、呼び出しごとの番号つきでかけらを送る。
- ログイン画面での先読みを、main.js から送るか、ログイン画面から送るか。
  - どちらでも、モデル名・`options`・判定の指示は、チャット画面と同じものを1か所から使う。
  - ずれると、モデルを読み込み直すか、キャッシュが効かない。
- `showTwoPartResponse` を、すでに出ている line の吹き出しを使えるように変えるやり方。
- `script.js` の `conversationHistory`・`recentLines`・`userEmotionHistory` の整理。要約の文と記憶の抽出は、今と同じ「発言と返事の文」の並びを使う。
