# 社員の管理 設計書

- 日付：2026-10-26
- 状態：実装済み（2026-10-27。7ef2fff・ac64eaa・783418f・ceacb17・14aee15・67f7021・220fa2c・c073c74）。設計は 2026-10-26 にユーザーが範囲と形を承認した

## 1. 背景と目的

### 背景
- 実在の社員を登録する手段がない。今は、デモ用の社員（seed）か、DB を直接触るしかない。
- パスワード変更（2026-10-20）とトークンの問題（2026-10-26）で範囲外にした「社員の登録・管理者によるリセット・退職者の設定」が残っている。
- 実際に会社で使うには、管理者がアプリの画面から社員のアカウントを扱えることが欠かせない。

### 目的
- 管理者が、アプリの画面から社員を登録し、直し、パスワードをリセットし、退職にし（戻すこともでき）、消せるようにする。
- 管理者が社員の本当のパスワードを知らないまま、アカウントを渡せるようにする（仮のパスワード＋最初のログインで変更）。

### 成功基準
- 管理者（A001）が「社員」タブで社員を登録すると、仮のパスワードが1回だけ表示される。その社員は仮のパスワードでログインし、新しいパスワードに変えてからチャットに入れる。
- 仮のパスワードのままでは、パスワードの変更とログアウト以外のサーバーの機能を使えない。
- リセットすると、その社員のログインがすべて切れ、次のログインで新しいパスワードに変えることになる。
- 退職にすると、その社員はすぐ使えなくなる。在籍に戻すと、また使える。
- 退職にした社員だけを消せる。消すと、感情ログも一緒に消える。
- 自分自身を退職にする・消す・管理者から外す・リセットすることはできない。在籍している管理者が1人もいなくなる操作もできない。
- 管理者の操作が、DB の表に残る。
- 「社員」タブに、感情に関わる情報が一切出ない。
- `npm test` がすべて通る。

## 2. 決定事項（2026-10-26 にユーザーと合意したもの）

1. 登録は、画面で1人ずつ行う。CSV などでまとめて登録する機能は作らない（あとから足せる）。
2. 社員の管理を使えるのは、今の管理者（`is_admin = 1`）と同じ人。役割は分けない。
3. 登録とリセットでは、サーバーが仮のパスワードを作って画面に1回だけ出す。本人は最初のログインで必ず変える。
4. 画面は、ダッシュボードのウィンドウに「集計」「社員」のタブを置いて切り替える。
5. 辞めた社員は、退職にする（戻せる）。そのうえで、消すこともできる。
6. 管理者の操作は、DB に記録を残す。画面には出さない。
7. 新しいパスワードを決める画面は、ログイン画面の続きに出す（チャットに移る前）。
8. 「社員」タブの配置は「一覧＋右に詳しい欄」（試作 A）。右の欄の場面の見せ方（4.4 の①〜③）も、ユーザーが試作を見て承認した。
9. 4.1〜4.5 のうち「Claude の判断」と書いたものは、まとめの形でユーザーに見せて承認を得た。
10. 最初の管理者と、管理者がパスワードを忘れたときは、サーバーでコマンドを動かして作る・リセットする（4.3 の「管理者を作る道具」）。サーバーを触れる人は DB も触れるので、守りは弱くならない。

## 3. 調べて分かったこと（2026-10-26）

- **DB**（`tumugi_server/sql/schema.sql`）
  - `employees`：`employee_code`（UNIQUE、`VARCHAR(20)`）、`password_hash`、`display_name`、`department`、`is_active`、`is_new_grad`、`is_admin`。照合順序は `utf8mb4_general_ci` なので、社員IDの重複は大文字・小文字を区別せずに判定される。
  - `emotion_logs` と `auth_tokens` は、`employees(id)` に `ON DELETE CASCADE`。社員を消すと一緒に消える。
  - `login_attempts` は `employee_code`（文字）で持っていて、外部キーはない。社員を消しても残る。
  - `schema.sql` は、DB のボリュームが空のとき（初回）にだけ実行される。今ある DB に列や表を足すには、別に SQL を流す必要がある。
- **管理者の確かめ方**：`dashboard_data.php` は、`verifyToken()` のあとで `SELECT is_admin FROM employees WHERE id = :id AND is_active = 1` を行い、管理者でなければ 403「この機能を利用する権限がありません」を返す。
- **トークン**：`verifyToken()`（`includes/db.php`）は、在籍している社員の、期限内のトークンだけを通す。`logout.php` は `verifyToken()` を使わない。`change_password.php` は `verifyToken()` を使う。
- **ログイン**：`login.php` は `is_active = 1` の社員しかログインさせない。失敗は `login_attempts` に数え、15分に5回で止める（`includes/login_guard.php`）。
- **アプリのログイン**（`js/auth.js` の `submitLogin()`）：トークンなどを保存し、入力したパスワードから記憶の鍵を作り（`memoryUnlock`）、チャットに移る（`loginSuccess`）。
- **パスワードの決まり**：`js/password.js` の `validateNewPassword({ current, next, confirm })`。サーバーの `change_password.php` と同じ決まり（8文字以上、72バイトまで、今と違うもの）。
- **記憶**：鍵はパスワードから作る。パスワードがリセットされると、前の記憶は読めず、読もうとしたときに消される（`main.js` の `memory:get`）。
- **デモデータ**（`tumugi_server/tools/seed_demo.php`）
  - デモ用ではない社員が1人でもいると、何もせずに止まる（`Exited (1)`）。
  - 足りないデモ用の社員は、起動のたびに足す。
- **ダッシュボードのウィンドウ**（3d4406e）：チャットの上にモーダルで開く別のウィンドウ。「チャットに戻る」で閉じる。ログアウトすると閉じる。
- **画面の決まり**：CSP で HTML の `onclick` が使えない（JS で登録する）。Electron では `confirm()`・`alert()` を使わない。
- **権限**：`main.js` は、画面からの権限の要求をすべて断っている（クリップボードへの書き込みも含む）。
- **展示モード**：パスワードの変更欄は、展示モードでは出さない（`window.electronAPI.isExhibitMode()`）。
- **中継の許可リスト**：`net-policy.js` の `ALLOWED_REQUESTS.server` は5組（login・save_emotion・dashboard_data（GET）・change_password・logout）。テストは `test/net-policy.test.js`。
- **テスト**：今は88個。PHP には自動のテストがない。

## 4. 設計

### 4.1 全体の決まり

- **匿名の方針を崩さない**：「社員」タブと、そのための API は、感情に関わる情報（感情ログ、危機、ハラスメント、最後に使った日時、ログの件数など）を一切扱わない。
- **仮のパスワードを残さない**：仮のパスワードは、作った API の応答で1回だけ返す。DB にはハッシュだけを入れる。ログ・`console`・操作の記録には書かない。
- **権限はサーバーが毎回確かめる**：どの操作でも、サーバーがそのたびに「在籍している管理者か」を DB で確かめる。画面の出し分けは見た目だけ。
- **管理者がいなくなる操作を止める**：自分自身を退職にする・消す・管理者から外す・リセットすることはできない。在籍している管理者が0人になる操作もできない。
- **ローカル完結**：仮のパスワードを届ける仕組み（メールなど）は作らない。管理者が本人に直接伝える。
- **確認は画面の中で行う**：`confirm()`・`alert()` は使わない。

### 4.2 DB

**`employees` に列を足す**
```sql
must_change_password TINYINT(1) NOT NULL DEFAULT 0  -- 1：仮のパスワードのまま（次のログインで変える）
```

**操作の記録の表を作る**（社員を消しても記録が残るよう、外部キーにせず社員IDを文字で持つ。Claude の判断）
```sql
CREATE TABLE admin_audit_logs (
  id           INT AUTO_INCREMENT PRIMARY KEY,
  admin_code   VARCHAR(20)  NOT NULL,   -- 操作した管理者の社員ID
  action       VARCHAR(20)  NOT NULL,   -- create / update / reset_password / deactivate / reactivate / delete
  target_code  VARCHAR(20)  NOT NULL,   -- 対象の社員ID
  detail       VARCHAR(255) NULL,       -- update のとき、変えた項目の名前（例：department,is_admin）。値は入れない
  created_at   TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;
```

**今ある DB に足す SQL**（Claude の判断）
- `tumugi_server/sql/migrations/2026-10-26-employee-management.sql` に、上の `ALTER TABLE` と `CREATE TABLE` を置く。`down -v` で作り直すと、データがすべて消えるため。
- `schema.sql` にも同じ列と表を足す（新しく作る DB は、最初からこの形になる）。
- README に、今ある DB への流し方を書く（リポジトリのルートから、`docker compose exec -T db` に流す形）。

### 4.3 サーバー

**共通**
- `includes/` に、管理者を確かめる関数を足す（`requireAdmin()`）。
  - `verifyToken()` が通らなければ 401「認証が必要です」。
  - 在籍している管理者でなければ 403「この機能を利用する権限がありません」。
  - 通れば、操作した管理者の `id` と `employee_code` を返す。
  - `dashboard_data.php` の今の確かめも、この関数に置き換える（確かめ方を1か所にするため。Claude の判断）。
- `verifyToken()` は、`must_change_password = 1` の社員のトークンを通さない。ただし `change_password.php` だけは通す（引数で切り替える。形は作り手に任せる）。
- 仮のパスワードを作る関数を足す。
  - 12文字。使う文字は、英大文字・英小文字・数字から、見間違えやすい `0 O o 1 l I` を除いたもの。`random_int()` で選ぶ（Claude の判断）。

**`login.php`**
- 応答に `must_change_password`（真偽値）を足す。ほかは変えない。

**`change_password.php`**
- `verifyToken()` を、`must_change_password = 1` でも通す形で呼ぶ。
- パスワードを更新するとき、同じ `UPDATE` で `must_change_password = 0` にする。ほかは変えない。

**社員の管理の操作**（ファイルの分け方とパスは作り手に任せる。どれも最初に `requireAdmin()` を通す）

| 操作 | 受け取るもの | 確かめること（止まったときの応答） | すること | 記録の action |
|---|---|---|---|---|
| 一覧（GET） | なし | — | 全社員の `employee_code`・`display_name`・`department`・`is_new_grad`・`is_admin`・`is_active`・`must_change_password` と、在籍の社員の部署の一覧（退職者だけの古い部署は選ぶ候補に出さない。Claude の判断）と、操作している管理者の社員ID（画面が自分自身の行を見分けるため）を返す | 残さない |
| 登録 | 社員ID・名前・部署・新卒・管理者 | 入力の形（400）、社員IDの重複（409） | 仮のパスワードのハッシュと `must_change_password = 1` で `INSERT`。応答で仮のパスワードを返す | `create` |
| 直す | 社員ID・名前・部署・新卒・管理者 | 入力の形（400）、社員がいない（404）、自分を管理者から外す・最後の在籍の管理者を外す（400） | `UPDATE`（社員IDは変えない。退職中の社員も直せる。Claude の判断） | `update`（変えた項目の名前を `detail` に） |
| リセット | 社員ID | 社員がいない（404）、自分自身（400） | 仮のパスワードに替え、`must_change_password = 1`。その社員のトークンをすべて消し、`login_attempts` の失敗を消す。応答で仮のパスワードを返す | `reset_password` |
| 退職にする | 社員ID | 社員がいない（404）、自分自身・最後の在籍の管理者（400） | `is_active = 0`。その社員のトークンをすべて消す | `deactivate` |
| 在籍に戻す | 社員ID | 社員がいない（404） | `is_active = 1`（パスワードは変えない。Claude の判断） | `reactivate` |
| 消す | 社員ID・確かめの社員ID | 社員がいない（404）、在籍中（400）、確かめの社員IDが合わない（400） | `login_attempts` のその社員IDの行を消し、`employees` から消す（感情ログ・トークンは `CASCADE` で消える） | `delete` |

- 入力の形（Claude の判断）
  - 社員ID：英数字・`-`・`_` の1〜20文字。登録のときは、`CLI`（大文字・小文字を問わない）も使えない（管理者を作る道具の操作の記録と、見分けがつかなくなるため）。形の確かめが先で、そのあとにこれを確かめる。
  - 名前・部署：前後の空白を除いて1〜50文字（`mb_strlen`）。
  - 新卒・管理者：真偽値。
- 書き込みが2つ以上ある操作（記録を含めて、一覧以外のすべて）は、1つのトランザクションで行う。
- 「最後の在籍の管理者」の判定は、同じトランザクションの中で在籍の管理者を数えて行う（ほかの管理者が同時に操作しても崩れないように、行をロックする）。
  - 操作する人は在籍の管理者なので、ふつうは「自分自身への操作を止める」だけで足りる。この判定は、2人の管理者が同時にお互いを外すような場合の守り。
- 応答のエラーは、ほかの API と同じく `{"error": "…"}`（日本語）で返す。

**管理者を作る道具**（`tumugi_server/tools/admin_setup.php`）
- 使い道：実運用の最初の管理者を作る。管理者がパスワードを忘れて、ほかに管理者がいないときに戻す。
- 動かし方：リポジトリのルートから `docker compose exec app php /var/www/tumugi/tools/admin_setup.php <社員ID> [名前] [部署]`。いつも動いている app のコンテナで動かす（新しい起動の設定は足さない。Claude の判断）。
- コマンドから動かしたときだけ動く（`PHP_SAPI !== 'cli'` なら何もせずに終わる）。`tools/` は URL で公開されていない（公開は `/api` だけ）。
- その社員IDの社員がいないとき：名前と部署が必要（なければ使い方を出して終わる）。管理者・在籍・`must_change_password = 1` で作る。
- その社員IDの社員がいるとき：社員IDだけを指定する。管理者・在籍にし、仮のパスワードに替え、`must_change_password = 1` にする。その社員のトークンとログインの失敗を消す。名前や部署が付いているときは、何も変えず、仮のパスワードも出さずに、メッセージを出して終了コード1で終わる（新しい社員を作るつもりで、いる社員をリセットしてしまわないため）。
- 仮のパスワードは、作り方も扱いも 4.3 の「共通」と同じ。画面（ターミナル）に1回だけ出す。
- 操作の記録を残す（`admin_code` は `CLI`、action は作ったとき `create`、いたとき `reset_password`。Claude の判断）。そのため、社員ID「CLI」（大文字・小文字を問わない）は登録できない（画面からも、この道具からも）。

### 4.4 アプリ

**ログイン画面（`login.html`・`js/auth.js`）**
1. ログインの応答が `must_change_password: true` のとき、トークンなどは今と同じく保存する。ただし、記憶の鍵はまだ作らず、チャットにも移らない。
2. ログインの入力を隠し、「新しいパスワードを決めてください」の入力（新しいパスワード、もう一度）に切り替える。
   - 説明：「管理者から伝えられた仮のパスワードは、ここで新しいパスワードに変えてください」。
   - 入力した仮のパスワードは、この画面のあいだだけ JS の変数に持つ。
3. 決まりの確かめは `js/password.js` の `validateNewPassword()` を使う（`current` に仮のパスワードを渡す）。`login.html` で `password.js` を読み込む。
4. `POST /change_password.php` が成功したら、新しいパスワードで記憶の鍵を作り（`memoryUnlock`）、チャットに移る（`loginSuccess`）。
5. 失敗したとき
   - 401：ログインの入力に戻し、「もう一度ログインしてください」と出す。
   - 400・403・429：サーバーのメッセージを出す。
   - サーバーに接続できない：「サーバーに接続できませんでした」。
6. 「やめる」を押すと、`logout()` と同じく、サーバーのトークンを消してからログインの入力に戻す（Claude の判断）。
7. 変えずにアプリを閉じた場合、次も仮のパスワードでログインして、この画面からやり直す。

**ダッシュボードのウィンドウ（`admin-dashboard.html`）**
- 見出しの下に「集計」「社員」のタブを置く。開いたときは「集計」。今の内容は「集計」に入れる。
- 展示モードでは「社員」タブを出さない（来場者が共用のアカウントで社員を消せないように。Claude の判断）。

**「社員」タブ（配置は試作 A）**
- 左：一覧
  - 上に検索の欄（社員ID・名前で絞り込む）と「＋ 新しい社員」のボタン。
  - 各行に社員ID・名前・部署と、札（新卒・管理者・退職・仮のパスワード）。
  - 退職の社員は、色を薄くして在籍の社員のあとに並べる（Claude の判断）。
- 右：詳しい欄。次の場面を切り替えて出す。
  - 何も選んでいない：「社員を選んでください」。
  - 登録：社員ID・名前・部署・新卒・管理者を入れて「登録する」。
    - 部署は、今ある部署から選ぶか、「新しい部署」を選んで入れる（打ち間違いで部署が分かれると、集計の人数が足りずに表示されなくなるため。Claude の判断）。
  - 社員を選んだとき
    - 名前・部署・新卒・管理者を直して「保存する」（社員IDは表示だけ）。
    - 在籍中なら「パスワードをリセット」「退職にする」、退職中なら「在籍に戻す」「消す」。
    - 自分自身の行では、できない操作のボタンを押せなくし、理由（「自分自身は〜できません。自分のパスワードは、チャットの『設定』から変えてください」）を出す。
  - ① **仮のパスワードの表示**（登録・リセットのあと）
    - 「この画面を閉じると、二度と表示されません」と書き、仮のパスワードを大きく出す。文字は選んでコピーできる（コピーのボタンは付けない。アプリが権限をすべて断っているため。Claude の判断）。
    - 「本人に直接伝えてください。最初のログインで、本人が新しいパスワードに変えます」。
    - 「伝えたので閉じる」を押すまで、この表示のまま。
  - ② **リセットの確認**
    - 「この人のログインは、すべて切れます」「この人のつむぎの記憶は読めなくなり、消えます（元に戻せません）」を出し、「リセットする」をもう一度押してもらう。
  - **退職の確認**：②と同じく、何が起きるか（すぐログインできなくなる）を出してから、もう一度押してもらう（Claude の判断）。
  - ③ **消すときの確認**
    - 「この人の社員の情報と、感情ログがすべて消えます。元に戻せません。集計の数字も変わります」。
    - 社員IDを打ち込むと、初めて「消す」が押せる。
- 操作が終わったら、一覧をサーバーから読み直す。
- サーバーの応答が 401 なら `logout()`（ダッシュボードも閉じる）。それ以外のエラーは、右の欄にメッセージを出す。
- 社員の名前・部署など DB から来た文字は、必ず `escapeHtml()` を通すか `textContent` で出す。
- 画面に依存しない部分（入力の確かめ、絞り込み、自分自身・最後の管理者の判定、並べ方など）は、`js/` の別のファイルに分け、`node --test` のテストを足す（今の `password.js` と同じ形）。サーバーが最終的に確かめるので、ここは理由を先に出すため。

**`net-policy.js`**
- 社員の管理の API を、メソッドとパスの組で足す。テスト（許可した組・メソッドが違えば拒否）も直す。

**README**
- 「社員の管理」を機能の説明に足す（登録・リセット・退職・消す、仮のパスワードと最初のログインでの変更）。
- 「セキュリティ上の前提」に、仮のパスワードの扱い・操作の記録・自分自身と最後の管理者を守ることを足す。
- 今ある DB に列と表を足す手順（4.2）。
- デモの DB に本物の社員を足すと、次の起動でデモデータの投入が止まること（確かめで足した社員は、消してから起動し直す）。
- 「デモから実運用に切り替えるとき」に、最初の管理者を道具で作ること（4.3）と、実在の社員は「社員」タブで登録することを書く。
- 管理者がパスワードを忘れて、ほかに管理者がいないときは、道具でリセットすること。

### 4.5 確認の手順（ユーザーが行う）

管理者の操作は A001、一般社員の側は、確かめのために登録する社員で行う（E048 などデモの社員のパスワードは変えない）。
1つの PC のアプリには1人しかログインできないため、「ログインが切れる」ことは、DB のトークンの数で確かめる。
1. `npm test` がすべて通る。
2. 変えた・作った PHP に、文法の誤りがない（`php -l`）。
3. 今ある DB に、4.2 の SQL を流せる（列と表ができる）。
4. **登録**：A001 で「社員」タブを開き、確かめ用の社員を登録すると、仮のパスワードが1回だけ出る。同じ社員IDは登録できない（409）。
5. **最初のログイン**
   - 確かめ用の社員が仮のパスワードでログインすると、新しいパスワードの画面になる。
   - 決まりに合わないと理由が出る。変えるとチャットに入れ、「はじめまして」から始まる。
   - 一度ログアウトし、新しいパスワードでログインし直せる。
6. **仮のパスワードのまま使えない**：確かめ用の社員でチャットにいるあいだに、DB でその社員の `must_change_password` を1にすると、次の送信で 401 になり、ログイン画面に戻る。ログインし直すと、新しいパスワードの画面になる。
7. **直す**：名前・部署・新卒を直すと、一覧に出る。
8. **リセット**
   - 確かめ用の社員でログインし、ログアウトせずにアプリを閉じる（DB にトークンが残る）。
   - A001 でその社員をリセットすると、DB のその社員のトークンが0になる。
   - 仮のパスワードでログインし、変えると入れる。記憶は「はじめまして」から。
9. **退職・在籍に戻す**：確かめ用の社員を退職にすると、ログインできない。在籍に戻すと、ログインできる。
10. **消す**：在籍中の社員には「消す」が出ない。退職にしてから、社員IDを打ち込むと消せる。一覧から消える。
11. **守り**
    - A001 の行では、退職・消す・管理者から外す・リセットができない。
    - 在籍の管理者が A001 だけのとき、ほかの社員を管理者にしてから外すことはできるが、A001 を外すことはできない。
12. **記録**：`admin_audit_logs` に、4〜11 の操作が残っている。仮のパスワードはどこにも入っていない。
13. **展示モード**（`npm start -- --exhibit`）：「社員」タブが出ない。
14. **管理者を作る道具**
    - 新しい社員IDで動かすと、管理者が作られ、仮のパスワードが出る。その社員でログインすると、新しいパスワードの画面になり、変えるとダッシュボードの「社員」タブを使える。
    - 名前と部署を付けずに新しい社員IDで動かすと、使い方が出て何も作られない。
    - `http://127.0.0.1:8080/tools/admin_setup.php` は開けない（404 か 403）。
15. **後片付け**：確かめ用の社員（道具で作った管理者も）を消し、`docker compose` を起動し直すと、デモデータの投入（seed）が止まらない。

## 5. 範囲外

- CSV などでまとめて登録する。
- 役割を分ける（ダッシュボードを見る人と、アカウントを扱う人）。
- 仮のパスワードの有効期限。
- 仮のパスワードを本人に届ける仕組み（メールなど）。
- 操作の記録を画面で見る。
- 社員IDの変更。
- `login_attempts` の掃除（たまり続ける）。
- 消した社員の、それぞれの PC に残るデータ（暗号化された記憶・感情ログ送信の同意）。サーバーからは消せない。記憶は本人のパスワードがないと読めない（Claude の判断）。

## 6. リスクと対策

- **消すと元に戻せない**：退職にした社員だけを消せる。社員IDを打ち込む確認を付ける。
- **管理者がいなくなる**：自分自身への操作を止め、最後の在籍の管理者を外す操作を、トランザクションの中で止める。
- **管理者がパスワードを忘れて、ほかに管理者がいない**：サーバーで道具を動かしてリセットする（4.3）。
- **リセットで記憶が消える**：リセットの確認で、はっきり伝える。
- **仮のパスワードが漏れる**：画面に1回だけ出し、DB にはハッシュだけを入れる。仮のパスワードのままでは、パスワードの変更以外を使えない。
- **デモの DB に確かめ用の社員が残ると、デモが起動しない**：確認の手順の最後で消す（4.5 の14）。README にも書く。

## 7. 作り手に任せること

- 社員の管理の API のファイルの分け方とパス（1操作1ファイルか、まとめるか）。
- `verifyToken()` で `must_change_password` を切り替える引数の形。
- 4.4 にない画面の文言と、CSS の細かいところ。
- 画面に依存しない部分を、どのファイルにどう分けるか。
