2. **ログインの情報を、PC のディスクに保存しないようにした（レビューの B9）。**
   - 前は、ログインの情報（トークン・社員ID・部署・期限・管理者か）を、OS の仕組み（safeStorage）で包んで、アプリの保存のファイルに書いていた。ログアウトせずに閉じると、その値がディスクに残った。
   - 今は、アプリの中心のプロセス（main.js）のメモリにだけ置く。画面の側のコードは変えず、保存の入口（取り出す・保存する・消す）で、ログインの情報のキーだけをメモリに回す。アプリを閉じると消える。
   - ユーザーが決めたこと：
     - 対象は、ログインの情報の5つすべて。感情ログの同意（だれが同意したか）は、今までどおり保存する。
     - 前の版が保存のファイルに残した分は、起動のときに消し、残っていたトークンはサーバーでも無効にする。
   - まとめ役が決めたこと：
     - メモリに置くだけなので、保存の順番待ちには入れない。ログアウトのときにも消す。
     - 起動のときの片付けは、画面を開くのを待たせずに行う。保存のファイルにあるキーだけを消す（ないキーを消しても、毎回ファイルを書くため）。トークンが残っていれば、画面のログアウトと同じ形でサーバーに送る。そのために、サーバーとの中継の中身を関数に分けた（中継の動きは同じ）。
     - テストは3個。ログインの情報のキーが5つで、保存してよいキーの中にあること。画面のコードのキーの名前と、ちょうど同じこと。保存の3つの入口が、保存のファイルより先に、ログインの情報かを見ること。
     - README に「その値は PC のどこにも残りません」と書く予定だったが、OS がメモリの中身をページファイルに書くことがあるので、「保存のファイルには残りません」に弱めた。
   - 確かめでは、直す前の版（セッション22で、配る形の確かめに作ったもの）でログインしてから、ログアウトせずに閉じた。そのあと直した版を起動すると、残っていたトークンがサーバーでも無効になった。そのあとログインしても、保存のファイルにログインの情報が書かれないことを、サーバーの記録と、保存のファイルのキーの名前で確かめた。
3. **感情ログの値を、画面のログ（開発者ツールの console）に出さないようにした（レビューの E6）。**
   - 前は、同意していないとき（感情ログを送らないとき）に、送るはずだった値（感情・危機か・ハラスメントの種類）を、送ったあとに、サーバーの返事（スコア）を、画面のログに出していた。開発者ツールを開くと、社員の気持ちが見えた。
   - 2か所とも、文だけを出すようにした（「同意していないため送信をスキップ」「記録完了」）。
   - ユーザーが決めたこと：
     - ログの行は残し、中身だけ消す（どこを通ったかは分かるように）。
     - キーワードに当たったが、判定で危機でもハラスメントでもなかったときのログ（セッション16の A1 で足したもの）は、そのまま。発言も理由も出しておらず、キーワードに当たったことは、相談先の案内として画面にも出るため。
     - テストを足す。
   - まとめ役が決めたこと：
     - テストは、アプリの JS の console の呼び出しの引数から、文字列の中身を除いた名前を拾い、渡さない名前の一覧（気持ちと安全の判定・発言と会話の履歴・記憶・サーバーの返事・パスワード・トークン）と照らす。テンプレートの中の式と、何行かにまたがる呼び出しも見る。
     - 名前で見るので、一覧にない名前の変数で渡すのは防げない。付け忘れ・戻し忘れの見張りとして使う。
     - 読み方そのもののテストと、拾えた呼び出しの数の下限も足した（読み方が変わって、何も拾えないまま通るのを防ぐ）。
   - 確かめでは、同意していない社員で話しかけ、開発者ツールに文だけが出ることと、サーバーに感情ログが送られていないことを確かめた。同意している道（「記録完了」）は、デモの記録を増やさないため、画面では確かめず、テストに任せた。
4. **記憶の抽出のあいだに、記憶の画面で直した記憶が元に戻らないようにした（レビューの E5）。**
   - つむぎは、3往復に1回、会話から覚えることを裏で抜き出す（記憶の抽出）。前は、始める前に記憶の写しを取り、Ollama の返事を待ってから、その写しに足して保存していた。待つあいだ（数秒、CPU だけの PC では十数秒以上）に、本人が記憶の画面で項目を削除・書きかえ・「全部忘れる」をすると、その保存で元に戻った。「全部忘れる」なら、全部が戻った。
   - 今は、記憶が変わった回数を数え、抽出の保存の直前に、始めたときの回数と比べる。変わっていたら、その回の抽出の結果は入れない。
   - ユーザーが決めたこと：
     - その回の結果は捨てる。失うのは、その3往復から覚えるはずだった分だけ（3往復たまる前にアプリを閉じたときと同じ）。本人が触った項目だけを除いて足す案は、AI が同じことを別の名前の項目で返すと、消した中身が戻るので選ばなかった。
     - テストを足す。
   - まとめ役が決めたこと：
     - 回数は、記憶を置きかえる3つの関数（読み込み・保存・全部忘れる）で増やす。
     - 捨てた3往復の分は、次の抽出にも回さない。回すと、本人が消した中身を、AI がまた拾うことがあるため。
     - テストは、ソースの並びで見る。待つ前に回数を覚え、待ったあと・保存の前に比べ、そのあいだに待たないこと。記憶を置きかえる関数が、どれも回数を増やすこと。画面のコード（script.js）は、画面の中でしか動かないため。
   - ログアウトのときは、画面ごと読み直すので、途中の抽出が次の社員の記憶に混ざることはない（もともと）。
   - 確かめでは、開発者ツールから抽出を呼び、待つあいだに項目の削除と「全部忘れる」をして、どちらも元に戻らないことと、何もしなければ今までどおり覚えることを確かめた（最後に、元の記憶に戻した）。
5. どれも小さい直しなので、設計書は作らず、決めたことはこのログに書いた。直すたびに、ユーザーがテストを実行し、画面で確かめた。

## 学んだこと

- 秘密の値をディスクに置かない直しでは、新しい版で書かないだけでなく、前の版が残した分の片付けも要る。片付けの確かめには、直す前の版が要る（B9）。
- 「どこにも残らない」のような言い切りは、OS の動き（ページファイル）まで含めると言えないことがある。README は、確かめられる範囲（保存のファイル）で書く（B9）。
- 画面のログは、開発者が見るものでも、社員の気持ちを出さない。トラブルの対応で開く人が、社員の気持ちを見てよい人とは限らない（E6）。
- 裏で待つ処理は、待つあいだに本人が変えたものを上書きしないかを見る。始める前の写しに足して保存する形は、そのあいだの変更を消す（E5）。
- 画面の確かめは、サーバーや Ollama の記録で裏を取る。B9 では、これで手順の抜けに気づけた。
