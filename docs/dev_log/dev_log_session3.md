## 決めたこと

- **モデル。** Gemma 4 E4B を各 PC で動かす。
- **キーワード。**
  - 見逃しを減らすことを優先する。
  - 仕事の話でも出る言い回し（「楽になりたい」「終わらせたい」「飛び込み営業」）は入れない。
  - 「遺書」も入れない。ドラマや小説の話でも出るため。LLM は「遺書みたいなものを書いてみた」を拾い、ドラマの遺書のシーンの話は危機と判定しなかった。
- **言い方。** 「〜な感じ？」の型は残し、ほかの受け止め方を増やす。
- **判定の方式。** 判定専用の呼び出しで、理由を先に書かせる。
  - 直前の2往復を渡す。
  - 考えるモードは使わない。精度は上がらず遅いうえ、考えるかどうかをモデルが自分で決めるので、時間が読めない。
  - temperature は 0。
  - 理由の文は、発言の中身を含むので、保存も表示もしない。
- **流れ。** キーワード → 判定 → 返事。危機なら返事を作らない。判定のぶん、毎回の待ち時間は GPU で約3秒、CPU だけ（事務用 PC に近い）で約12秒増える（そのあとの速さの改善で、全体としては直す前より短くなった）。
- **返事の欄。** crisis と harassment を返事から外し、4つの欄に戻す。返事の入力が約400語減る。
- **危機の発言を会話の流れに残す。** キーワードで判定したときも同じ。次の判定とつむぎの返事が、前に危機があったことを知ったうえで動けるようにするため。アプリで確かめたところ、危機のあとの「ありがとう、ちょっと落ち着いた」では案内は続けて出なかった。
- **「家族に迷惑かけてばかり」で案内が出ることは、そのままにする。** 不眠のあとのこの発言で、危機と判定された。負担に感じている気持ちは危険のサインとしてよく挙げられるものなので、「見逃しを減らす」方針どおりの動きとして受け入れる。
- **num_ctx。** すべての呼び出しを 8192（`OLLAMA_NUM_CTX`）にそろえる。
- **プロンプトの並べ方。** 変わらないキャラクターの指示 → ときどき変わる記憶・要約 → 会話の流れ → 今回の発言 → 毎回変わる動的ノート、の順にする。動的ノートは「ここから下はつむぎへの指示で、ユーザーの発言ではない」と区切って付け、会話の流れには残さない。
- **記憶の抽出は3往復に1回。** 3往復分をまとめて渡す。抽出の中身は、毎回抽出していたときと同じ程度だった。3往復に満たないうちにアプリを閉じると、その分は記憶されない。
- **CPU だけの PC 向けの対策は、あとで別のテーマにする。** 判定と返事で入力の前半を共有する作りにすれば約10秒をねらえるが、判定の作りが変わり、精度の測り直しが必要になるため。
- **「誰が困っているか」は、管理者に個人を見せることでは解かない。**
  - ストレスチェック制度と同じく、「組織には集計だけ、個人の支援は本人の申し出で専門職へ」と道を分ける。ダッシュボードは匿名のままにする。
  - 理由：見られると分かれば本音を書かなくなる。AI の判定は外れる（見逃しも誤検知もある）。ハラスメントの加害者が管理者の側にいることがある。同意画面の「管理者は個人ごとの詳細は見られず」という約束を変えることになる。
  - 本人が選んだときだけ、相談担当（産業医・保健師など、上司や人事とは別の人）に名前が届く機能を、あとで作る。
- **ダッシュボードの最低人数は10名。** ストレスチェック制度の集団分析の目安（10人を下回る集団の結果は、全員の同意がない限り事業者に渡さない）に合わせた。判定には、在籍人数ではなく、直近7日間に記録がある在籍社員の人数を使う。
  - 平均は社員ごとの平均の平均にする。ログの件数で重みを付けると、よく話す人の気分でグループの値が決まってしまうため。
  - 危機検知とハラスメントは、該当した人数で3段階に出す（0人はなし、1〜9人は「あり」だけ、10人以上は件数）。
  - デモは各部署12名にした。10名ちょうどだと、記録が7日より古くなる人が1人出ただけで部署が消えるため。
- **記憶はパスワードから作った鍵で暗号化する。**
  - このアプリは起動のたびにパスワードを聞くので、使い勝手は変わらない。同じ Windows アカウントを使う同僚も、会社の管理者も読めない。
  - パスワードをリセットすると、それまでの記憶は読めなくなり、消して新しく始める。
  - 守れないのは、本人のパスワードを知っている人と、本人がログイン中に動くウイルス。
  - 以前の共有の記憶は、誰のものか分からないので引き継がずに消す。
- **確認は `confirm()` を使わず、画面の中で行う。** キャラ設定の画面（社員の画面からは外してある）に2か所残っているが、今回は触らない。
- **表情と感情を分ける。**
  - 返事の emotion は、つむぎの表情だけに使う。ユーザーの感情は別に決めて、感情ログと「感情の流れに注意」の判断に使う。
  - ユーザーの感情は happy（嬉しい・楽しい）／normal（普段どおり）／tired（疲れ）／anxious（不安・心配）／angry（怒り・いらだち）／sad（悲しい・落ち込み）の6つに作り直す。「驚き」は気分の良し悪しを表さず、「疲れ」がなかったため。スコアは未定。
  - 判定に失敗したときは、感情ログを送らない。Ollama が失敗したときの代わりの返事で normal を送っている問題も直す。
  - ユーザーの感情を判定の呼び出しで決める案は採用しない。危機の見逃しが増えたため。

## つまずいたこと

- **考えるモードで、返事が空になった。**
  - 原因：Gemma 4 は、何も指定しないと考えるモードで動く。考える部分も num_predict に数えられるので、350 を使い切っていた。返事も、記憶の抽出も、要約も空振りしていた。
  - 対策：/api/chat の呼び出しすべてに `think: false` を付けた。考えるモードのないモデルに付けても、エラーにはならない。
- **測定ではうまくいったのに、アプリでは動かなかった。**
  - 原因：測定のスクリプトは `think: false` を送っていたが、アプリは送っていなかった。
  - 教訓：測定は、アプリと同じリクエストで行う。
- **`think: true` とスキーマを一緒に付けると、考えなかった**（Ollama 0.40.3）。think を付けないと、スキーマ付きでも考えた。
- **main.js の作業中の変更が、前のセッションの守り（cloud モデルの拒否・スペルチェックの停止）を消していた。** `git restore` でコミット済みの状態に戻した。
- **既定のプリセットが更新されていなかった。**
  - 原因：初回起動時に localStorage へ保存した写しを、ずっと使い続けていた。プロンプトを直しても、アプリには届かなかった。
  - 対策：既定のプリセットは、常にコードの `DEFAULT_PROMPT_TEMPLATE` を使うようにした。
- **CPU だけのときのキャッシュの結果が、10/9 と 10/13 で食い違った。**
  - 10/9 はキャッシュが効いていた（26秒 → 3.7秒）。10/13 の判定の呼び出しは、指示が同じでも毎回入力を処理し直していた。
  - 原因：入力が約450語以下だと、キャッシュが一切効かない。約700語を超えると、2回目からは入力の処理が0.5〜0.7秒で済む（GPU でも CPU だけでも同じ。スキーマの有無は関係ない）。判定の呼び出しは約450語で、効かない側に入っていた。
- **並べ替えても、CPU だけでは速くならなかった。**
  - 原因：Ollama が覚えておける入力は2つまでだった。1回の発言で3種類の入力（判定・返事・記憶の抽出）を順に送ると、古いものから消え、返事の番にはキャッシュが残っていなかった。
  - 対策：記憶の抽出を3往復に1回にして、ほとんどの回で送る入力を2種類にした。
- **記憶の抽出を返事の入力の続きにする案は、抽出がほとんど空（{}）になった。** 返事の流れの中で頼むと、モデルが抽出をさぼる。速さでは一番だったが、採用しなかった。
- **この PC には GPU（RTX 3050）がある。** 測定で「標準の設定」と呼んでいたのは GPU で動いた結果で、事務用 PC に近いのは「CPU だけ」の数字のほう。
- **ログインとログアウトを繰り返すと、社員IDを打てなくなった。**
  - 原因：「全部忘れる」の確認に `confirm()` を使っていた。Windows の Electron では、この確認画面を閉じたあと入力欄に文字が入らなくなり、ページを移っても直らない（Electron の既知の不具合）。暗号化の確認の手順で「全部忘れる」を押して、初めて表に出た。
  - 対策：確認を画面の中で行うようにした（「全部忘れる」の場所が［消す］［やめる］に変わる）。
- **Git Bash から `docker compose run ... php -l /var/www/...` を実行すると、パスが `C:/Program Files/Git/var/www/...` に書き換えられた。** `MSYS_NO_PATHCONV=1` を付けて直した。
- **判定の呼び出しに欄を1つ足しただけで、危機の判定が変わった。** 言い回し1つで拾える文が入れ替わる、という前回の教訓どおりだった。判定の指示を変えるときは、必ず測り直す。

## 残っている課題

- **安全判定の既知の弱点**
  - 「今までありがとね」→「なんでもない、言っておきたかっただけ」は、どの方式でも拾えない。
  - 異動の引っ越しで身の回りを整理する話や、出張前のあいさつを、危機と判定する（「迷ったら true」のため）。誤検知すると相談先の案内が出て、管理画面のログにも危機として残る。
  - 「はっきり危機」と「気がかり」の2段階にし、気がかりのときはつむぎがやわらかく様子を聞く案がある（今回は見送り）。
  - 判定の指示を変えたら、測定し直す（言い回し1つで拾える文が入れ替わる）。
- **返事の言い方**
  - 「〜んだね」で終わる返事が 39% ある。
  - 発言の言葉をそのまま繰り返す返事が、まだ多い（会話で約7割）。
  - ときどき口調がずれる（「〜だろうに」「〜のね」「〜だい」）。share と question が一緒に出ることがある。
- **CPU だけの PC での速さ**
  - まだ1回の発言に約28秒かかる。いちばん重いのは判定の呼び出し（約13秒）で、入力が約450語と短いため、キャッシュが効かない。
  - 案：判定と返事で入力の前半（キャラクターの指示と会話の流れ）を共有する作りにする（約10秒の見込み。判定の精度の測り直しが必要）。小さいモデル（E2B）を使う。
- **8GB の PC で E4B が収まるかの確認。** CPU だけの PC 向けの対策と一緒に行う。
- **レビューで決めた順の改善の残り**：つむぎの表情とユーザーの感情を分ける（着手済み・未実装。ダッシュボードの閾値と記憶の暗号化は完了）。
- **本人が選んだときだけ相談担当につなぐ機能**：やると決めたが、着手時期は未定。相談担当をどう登録するか、通知をどう届けるかを決める必要がある。
- **インストーラーを作る前に必須**：package.json の build 設定、Electron の更新（`npm audit` もここで扱う）。
- **前回からの残り**：ローカル完結の低優先項目、移行の細かい改善、実在の社員の登録手段、社内サーバー・公開の前の項目、XAMPP の後片付け、社内 LAN 用の接続先の設定。
