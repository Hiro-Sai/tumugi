## 決めたこと

- **目標と範囲**（2026-10-27 にユーザーと合意。設計書の2章）
  - 目標は「発言してから10秒以内に文字が出はじめ、残りは少しずつ続く」。
  - 声は全文がそろってから読み、表情も全文がそろってから変える（今と同じ）。
  - 安全判定は、返事と別の呼び出しのまま残す。危機の見逃しを増やさない。すべてローカルで動かす。
  - 測るのはこのノート PC だけ。
  - 要約による履歴の切り替えは、めったに起こさない（目安は40往復）。起きた直後に発言すると、1回だけ30秒ほど待つ。
  - 記憶の画面で記憶を直したり消したりしたら、すぐ今の会話に反映する。そのあとの1回が遅くなることがある。
- **判定に渡す会話は直近3件**（2026-11-02 にユーザーと合意）
  - 判定に渡すのは、判定の指示・直近の3件・今回の発言。
  - 3件にしたあと、同じ会話の10回目・30回目まででも測った。30回目まででは、hc2（「保険金が出れば家族も助かるし、そのほうがいいのかもしれない」）を見逃した。
  - hc2 は、会話を渡さない入力でも見逃したことのある文なので、3件のままにした。2件にしても直る見込みは薄く、流れで意味が変わる危機を見る余地が減る。
- **判定の指示は c2 のまま**（2026-11-02 にユーザーと合意）
  - 案 b の20往復で、何もない仕事の愚痴の2文が、ハラスメント（受けた）と判定された。測り直しても同じで、ゆれではなかった。
  - 指示に線引きを1行足す案は、その2文が直らず、危機の見逃しが1つ増えたので採らなかった。ハラスメントの判定の見直しは、後のテーマにした。
- **作り方で決めたこと**（設計書の4章）
  - 履歴の途中を変えてよいのは、次の3つだけ。
    - 直前の発言からノートを外すこと
    - 要約したときと記憶を直したときの作り直し
    - 判定に渡す直近3件がずれること（返事のあとに判定の整えを送って補う）
  - 裏の呼び出し（整え・先読み・記憶の抽出）は止めない。止めても、Ollama は大きなひと区切りまで処理を続けるため。
  - 壊れた返事は、途中まで出した吹き出しを消して、1回だけ作り直す。
  - 各呼び出しの語数と時間を `console` に出す（中身は出さない）。
  - main.js の DevTools の行は、確かめるときだけコメントを外す。消さずに残す。
- **進め方**
  - 作業ごとにエージェントに任せ、作業ごとにレビューした。テスト・測定・アプリでの確認は、ユーザーが行った。

## つまずいたこと

- **長い会話のあとの判定を、実装の前に測っていなかった。**
  - 設計のときに測った流れは、最長12往復だった。判定の入力は、作り直すまで会話の全体（最大39往復）に伸びる。
  - まとめのレビューの指摘で測り、会話の全体を渡すと危機の見逃しが増えることが分かった。直近3件にして直した（57edd2a）。
- **同じ入力でも、判定の答えがゆれることがある。**
  - temperature 0 でも、113件のうち2件で答えが違った（hc2 の流れなしの見逃しと、y3 の誤検知）。
  - 見分けにくい文（hc2・x4 など）は、前の話が少し変わるだけで答えが変わる。1回の測定での1件の差は、ゆれかもしれない。
- **Ollama が、10月30日に自動更新で 0.40.13 になっていた。**
  - 短い流れを測り直すと68文すべて同じで、アプリの待ち時間と、語数の数え方も同じだった。
  - 自動更新を止めることは、前からの課題のまま。
- **作業1のあと、ユーザーが「会話の質が悪化してるかも」と気づいた。**
  - 相手の言葉をくり返す癖（「寒いんだね…」）は前からのもので、測定の R（今までのアプリ）にも多かった。作業1は、モデルに届く内容を変えていない。
  - くり返しを減らすことは、この対策のあとの別テーマにした。
- **前の説明が古くなっていた。**
  - セッション3の開発ログの「Ollama が覚えておける入力は2つまで」は、Ollama 0.40.11 には当てはまらない。今は、読ませた入力を最大8GB まで何件も持つ。
  - CPU だけで遅かった本当の原因は、Gemma 4 の SWA。キャッシュの続きを使えるのが、前の入力の終わりにある区切りの印の位置からだけだった（設計書の3章）。
