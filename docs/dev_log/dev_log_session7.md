## 決めたこと

- **範囲と形**（2026-10-26 にユーザーと合意。設計書の2章）
  - 登録は画面で1人ずつ行う。CSV でまとめて登録する機能は作らない。
  - 使えるのは今の管理者（`is_admin = 1`）と同じ人で、役割は分けない。
  - 登録とリセットでは、サーバーが仮のパスワードを作り、画面に1回だけ出す。届ける仕組み（メールなど）は作らず、管理者が本人に直接伝える（ローカル完結）。
  - 新しいパスワードを決める画面は、ログイン画面の続き（チャットに移る前）に出す。
  - 画面は、ダッシュボードのウィンドウに「集計」「社員」のタブを置いて切り替える。
    - 配置は「一覧＋右に詳しい欄」（試作 A）。
    - 右の欄は、場面に応じて次のものを出す。どれも試作を見て決めた。
      - ① 仮のパスワード
      - ② リセットの確かめ
      - ③ 消すときの確かめ（社員IDを打ち込む）
  - 辞めた社員は、まず退職にする（戻せる）。そのうえで、消すこともできる。
  - 管理者の操作は DB（`admin_audit_logs`）に残し、画面には出さない。
  - 最初の管理者と、管理者がパスワードを忘れてほかに管理者がいないときは、サーバーで道具（`tools/admin_setup.php`）を動かす。サーバーを触れる人は DB も触れるので、守りは弱くならない。
- **作り方で決めたこと**
  - 「社員」タブとその API は、感情に関わる情報（感情ログ・危機・ハラスメント・最後に使った日時・ログの件数）を一切扱わない。匿名の方針を崩さないため。
  - API は1操作1ファイルにした。
    - どれも最初に `requireAdmin()` で、在籍している管理者かを DB で確かめる。
    - 一覧以外は、記録を含めて1つのトランザクションで行う。
  - `verifyToken()` は、仮のパスワードのままの社員を、ふだんは通さない。通すのは `change_password.php`（`verifyToken(true)`）だけ。`logout.php` はもともと `verifyToken()` を使わない。
  - 仮のパスワードは12文字。見分けにくい文字（0・O・1・l・I など）を除いた英数字で作る。
    - DB にはハッシュだけを入れる。
    - ログ・`console`・操作の記録には書かない。
  - 新卒・管理者・在籍の値は、JSON の `true`／`false` だけを受け付ける。`"0"` などを、思わぬ意味に取らないため。
  - 社員IDの重複は、大文字と小文字を区別せずに判定し（`t902` と `T902` は同じ）、409 を返す。
  - 次の2つは、行をロックしてトランザクションの中で判定する。
    - 自分自身への操作（退職・消す・管理者から外す・リセット）を止める
    - 在籍している管理者が0人になる操作を止める
  - 道具は、コマンドからだけ動く。
    - apache.conf が `/api` しか出さないので、URL では開けない。
    - 記録の管理者の欄は `CLI` になる。
    - 仮のパスワードは、コミットが済んでから出す。
  - 画面
    - ①の仮のパスワードは、「伝えたので閉じる」を押すまで消えない。一覧のほかの行・「＋ 新しい社員」・「集計」タブを押しても消えない。
    - 送っているあいだは、ボタンを押せない（二度押しで2回送らない）。
    - DB から来た文字は、テキストとしてだけ出す（`innerHTML` を使わない）。名前が `<b>あ</b>` でも、文字のまま出る。
    - 展示モードでは「社員」タブを出さない。展示モードかどうかを確かめられなかったときも出さない。
    - 一覧は、全体を1つのグリッドにし、どの行も同じ列の幅を使う（CSS の subgrid）。
  - 画面に依存しない判定（入力の確かめ・絞り込み・並べ方・自分自身と最後の管理者の判定）は `js/employee-rules.js` に分けて、`node --test` で確かめる。サーバーが最終的に確かめるので、ここは理由を先に画面に出すためのもの。
- **進め方**
  - 作業ごとにエージェントに分けて任せ、作業ごとにレビューした。テストと動作の確認はユーザーが行った。
  - 確認では、デモの社員（E001〜E048・A001）のパスワードを変えない。確かめ用の社員 T901・T902 を使い、最後に消した。

## つまずいたこと

- **設計書に、最初の管理者を作る手段がなかった。**
  - 計画を書く途中で気づいた。デモから実運用に切り替えると、DB を作り直すので管理者が1人もいなくなる。
  - サーバーで動かす道具を足して、設計書にも書き足した（決定事項の10）。
- **確認の手順が、2人が同時にログインしていることを前提にしていた。**
  - 1台の PC のアプリには1人しかログインできない。
  - 「ログインが切れる」ことは、DB のトークンの数で確かめる形に直した。
- **移行の SQL を流す前に新しいコードが動くと、ログインできなくなる。**
  - `tumugi_server/` は動いているコンテナにそのままつながっていて、ログインが新しい列を読むため。
  - 作業3のコードを確かめる前に、先に流してもらった。README にも「新しいコードを使う前に流す」と書いた。
- **改行コードの思い違い。**
  - レビューで「JS のファイルは CRLF」と報告されたが、実際は LF だった。Git Bash の `grep` は、CR を数えないことがある。
  - Node でバイトを数えて確かめた。
- **「社員」タブの一覧で、札のない行の部署の位置がずれていた**（ユーザーが通しの確認で見つけた）。
  - 原因：行ごとに flex で幅を決めていたため、札の欄の幅の分だけ、名前と部署の欄の広さが行によって変わっていた。
  - 一覧全体を1つのグリッドにして直した（c073c74）。

## 残っている課題

- **まとめのレビューで「このままでよい」とした小さな指摘**：主なものは次のとおり。
  - 移行の SQL で、`ALTER` を `CREATE TABLE` より先に流している。
    - 途中で失敗すると、「Duplicate column なら済んでいる」という説明が当てはまらない。
    - 今ある DB には流し終えていて、実運用の DB は `schema.sql` から作るので、困る場面はない。
  - 思わぬ DB のエラー（デッドロックなど）では、JSON ではない 500 が返る。今までの API と同じで、画面は決まりの文を出す。
  - ログイン画面の2段目で、送っているあいだも「やめる」が押せる。
    - どちらに転んでも、本人が知っているパスワード（仮のものか、2回打った新しいもの）になる。
  - ①の仮のパスワードを出しているあいだにウィンドウの × で閉じると、パスワードは失われる。もう一度リセットすればよい。
    - × を止めると、Electron ではウィンドウを閉じられなくなるため、止めない。
- **社員の管理の範囲外にしたもの**（設計書の5章）
  - CSV でのまとめての登録
  - 役割を分けること
  - 仮のパスワードの有効期限
  - 届ける仕組み
  - 記録を画面で見ること
  - 社員IDの変更
  - `login_attempts` の掃除
  - 消した社員の PC に残るデータ
